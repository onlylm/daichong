# 每日核算任务数据库化

## 资金规则不变

每日 22:00 的任务只生成核算单，不调用支付宝、银行或其他付款渠道，也不主动减少代理收益余额。只有平台管理员录入已经完成的真实打款流水与付款凭证后，系统才写入收益扣减；之后仍需人工核销。

## 原有性能问题

旧任务针对每个启用代理分别执行以下操作：

- 解码该代理全部历史核算单，构造已归属订单集合；
- 解码该代理全部收益确认记录；
- 对每一笔候选订单分别查询原订单、付款尝试和履约记录；
- 再次解码全部钱包流水计算余额；
- 再次解码全部核算单计算待付款占用。

随着订单、流水和核算单增长，这条夜间任务会产生明显的查询放大和长事务，可能与工作台读取竞争 SQLite。

## 本次改造

- 由 SQLite 一次关联钱包收益确认、订单、实收付款、成功履约和启用代理，直接取得真实可核算候选。
- 使用 `json_each(orderIds)` 在数据库排除已经进入非作废核算单的订单；作废单仍允许后续重新纳入。
- 一次聚合候选代理的收益余额与待付款核算单占用，不再逐代理解码全部流水。
- 全局商品成本配置在每次生成中只读取一次，不再逐订单读取。
- 增加钱包收益确认创建时间及核算单状态索引。
- 补齐 SQLite 日期反序列化字段 `generatedAt`、`reconciledAt`，避免核算单日期在持久化读取后退化成字符串。

## 安全边界

候选仍必须同时满足：平台收款、非测试、未归档、实收金额等于订单金额、真实付款状态为已付、至少一次履约成功、收益确认金额大于零，且未归属非作废核算单。任一条件不满足都不会生成可付款核算单。

内存仓储保留原有完整逻辑作为测试回退；生产 SQLite 使用数据库化路径。

## 验证

SQLite 集成测试构造真实付款、成功履约、收益确认与钱包余额，确认生成金额、成本、利润和可付金额正确，并验证生成路径未调用逐单订单、付款、履约或全量操作记录读取。生成后同一订单不再成为下一期候选。

本地分支尚未部署生产。最终部署前须备份生产数据库，并用只读副本核对候选订单集合与现网人工账目。
