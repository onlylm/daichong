# 开放 API 并发幂等占位

版本：2026-10-01  
状态：本地实现与自动化验证完成，尚未部署生产。

## 修复的问题

旧的通用写接口先查询幂等结果，再执行操作，最后保存响应。两个相同请求并发到达时，都可能在响应尚未保存前通过首次查询，从而重复执行下单、付款码生成、充值提交、退款申请或 Webhook 测试。

## 当前规则

1. 请求通过认证后，在数据库写事务中按 `merchant + app + route + Idempotency-Key` 原子建立执行占位；
2. 同键不同请求体立即返回 `idempotency_conflict`；
3. 同键同请求正在执行时返回 HTTP 409、`idempotency_in_progress`、`retryable: true`，不会再次进入业务动作；
4. 首个请求成功后，占位原子转为完成记录并保存原 HTTP 状态与响应；后续请求返回原响应并带 `Idempotent-Replayed: true`；
5. 业务动作明确失败时，只释放由当前请求持有的占位，使原业务请求可以恢复；
6. 占位租约为五分钟。进程异常退出后，过期占位可由后续请求接管；接管者必须先查询原业务结果，底层订单号、退款号、任务和付款码仍各自执行业务级幂等保护。

历史完成记录没有 `state` 字段时按完成记录读取，升级后仍可重放，不需要批量改写历史数据。

## 自动化证据

- 人为阻塞首个下单请求时，第二个同键同正文请求返回“处理中”，业务动作只执行一次；
- 同一执行窗口中的同键异正文请求返回冲突；
- 首个请求完成后再次提交，状态码和订单号与原响应一致；
- 业务动作失败后占位被释放，原业务键可以成功恢复；
- 两个独立 SQLite 连接不能同时持有同一占位；租约接管后旧持有者不能覆盖新结果。

本阶段没有创建真实订单、调用真实支付、充值或退款，也没有部署生产。
