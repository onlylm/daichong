# CI 与仓库凭证防泄漏

日期：2026-10-01
状态：本地与 GitHub Actions 均已验证，未部署生产。

## 目标

代码进入远端前必须自动验证类型、测试、构建和工作台脚本语法，并阻止把生产凭证、SQLite 数据库、私钥、发布压缩包或本地浏览器产物提交到 Git。

## 已实现

- `.github/workflows/ci.yml` 在 `main`、`refactor/platform-rebuild` 的推送及所有拉取请求上执行。
- CI 固定使用 Node.js 24 和 `npm ci`，随后执行生产依赖漏洞审计与 `npm run check`。
- `npm run check` 首先执行 `npm run check:repo`，本地与 CI 使用相同的仓库卫生规则。
- 检查范围仅为 `git ls-files` 返回的跟踪文件，不读取被忽略的本地生产凭证文档内容。
- 禁止跟踪 `.env`、密钥文件、SQLite/DB 文件、发布归档、本地数据目录、浏览器验收产物和指定内部交接文档。
- 跟踪文件超过 5 MiB 会失败；文本文件发现私钥头、常见 API Token、GitHub Token 或云访问密钥格式会失败。

## 本地验证

```bash
npm run check:repo
npm audit --omit=dev --audit-level=high
npm run check
```

当前本地结果：仓库卫生检查覆盖 371 个已跟踪文件；生产依赖审计为 0 个已知漏洞；63 个测试文件、316 项测试通过，类型检查和构建通过。

远端 `validate` 工作流已实际执行成功。最近一次已留证的完整运行是提交 `6c444e0` 对应的 Actions #3，精确依赖安装、仓库卫生、生产依赖审计、类型检查、全量测试、构建和浏览器脚本语法检查全部通过。后续提交仍须各自通过同一门禁，不能沿用旧提交的成功结论。

## 发布要求

1. 目标提交的 `validate` 工作流必须成功。
2. GitHub 分支保护应要求 `validate / check` 通过后才能合并；这是仓库设置，需在远端配置后单独确认。
3. CI 成功不能代替发布前数据库备份、恢复验证、Worker 新鲜心跳、支付和供应配置核对。
4. 若凭证曾经进入 Git 历史，仅删除文件不够，必须立即轮换凭证并按事件处理流程评估历史清理。

## 边界

该检查用于防止常见误提交，不代替 GitHub Secret Scanning、专用密钥扫描器、依赖供应链审查或人工复核。内部交接文档继续只保存在受控本地目录，不上传代码仓库。
