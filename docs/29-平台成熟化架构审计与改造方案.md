# Tibo 平台成熟化架构审计与改造方案

日期：2026 年 9 月 30 日。适用对象：平台所有者及后续开发者。

本文结合本地源码、生产运行版本、只读业务数据和运行日志分析 Tibo 的异常处理、售后、财务、通知和代理商接入。结论是：现有支付、订单、履约、钱包、工单已经具备基础，不需要推倒重建；优先修正任务终态与财务口径，再把异常处理组织成可追踪的工作流程。单纯增加邮件、按钮和弹窗不能解决底层状态不一致。

本文是审计结果与待实施方案，不代表下述功能已经实现。此次未修改业务代码、部署版本、增减余额、发起支付或退款，也未发送邮件、执行本地测试。除另有说明，风险为源码中确认的实现问题，并非认定生产已经发生对应资金损失。

## 已确定的业务约束

1. 平台只有一名管理员。退款处理、调账、提现确认均由这一名管理员操作，不设置第二审批人或多级审批。操作确认、审计日志、幂等和冲正仍保留。
2. 代理商没有主动取消充值任务的权限。只有上游明确返回失败，并确认本次履约尝试已经结束，系统才结束该次尝试，并在订单权益仍有效时开放原订单重新提交。
3. 排队、处理中、超时、断网、上游人工核对和结果未知，都不是明确失败。继续核对原任务，不能因为等待较久、代理点击取消或本地报错，就释放为可重提。
4. 结束失败尝试不等于取消订单、自动退款或再次收费。历史任务必须保留；重新提交创建新的尝试编号，并防止与旧尝试并发执行。
5. 代理商可选 CDK 交付或自动直充。自动直充底层使用 CDK，失败后向终端客户呈现代理商自己的充值入口或链接，不默认展示明文 CDK。
6. 代理商自行开发自己的品牌网站和异常页面；平台提供稳定的接口、事件和开发文档，不把平台品牌强加到代理商的客户界面。
7. 平台承担的补差退款不减少代理商佣金。普通退款与补差退款是不同业务，不能混为一类处理。

## 优先修正的实现问题

### 任务本地取消可能放行重复履约

`cancelActiveForResubmit` 允许把已派发或运行中的任务直接记为 `agent_cancelled`，清除租约并开放重新提交，而没有获得上游取消或失败确认。工作台对进行中订单显示“取消”按钮，后端也有对应代理路由。

同时，收到上游事件时，已被本地标记为终态的任务会被直接忽略。两者组合可能导致：上游仍执行旧任务，本地已开放新任务，旧任务随后成功却不再正确推进订单。

这是第一优先级。前端去掉按钮不够，后端必须拒绝代理主动取消，统一重提资格判断。仅凭 `failed` 字符串或 `fallbackRechargeAvailable` 布尔值也不够，要区分失败来源与上游是否明确终结。

### 钱包佣金与订单佣金口径存在冲突

订单佣金计算为 `max(售价 - 供货价 - 普通退款累计, 0)`，补差退款不参与扣减。但钱包 `eligibleEarning` 要求普通退款累计必须为零；一旦普通部分退款发生，`reconcileEarnings` 可能将这笔订单已经入账的佣金目标直接归零。

例如售价 135、供货价 110，原佣金 25，普通退款 10 后，订单口径是 15，钱包路径却可能全冲回 25，而不是只冲回 10。另一个边界是纯补差累计退满后，支付状态变为 `refunded`，钱包资格过滤也可能把佣金清零；这与平台承担补差的规则不一致。

这两类是代码风险，此次生产样本没有观察到对应差异。应先统一佣金规则与入账资格，增加固定案例验证，再考虑历史补记；不能未经逐单核对就批量改余额。

依据：[订单佣金公式](C:/Users/Administrator/Documents/Codex/2026-09-25/quefa-multi-merchant-platform/outputs/quefa-open-platform/src/domain/money.ts:27)、[钱包资格与回冲](C:/Users/Administrator/Documents/Codex/2026-09-25/quefa-multi-merchant-platform/outputs/quefa-open-platform/src/operations/wallet.ts:414)。

### 查询钱包会触发记账

钱包汇总和部分管理查询会调用佣金核对逻辑，产生佣金入账或回冲。虽然代码定义了 `creditEarningOnFulfillmentSuccess`，此次源码检索未找到调用点，实际仍主要依靠查询或其他钱包操作触发补记。

应改为业务事件驱动：履约成功、退款成功与佣金变动在一致的事务边界内记录；查询只读。后台补偿任务可以补漏，但必须使用同一规则和唯一业务键，不能成为另一套佣金口径。

依据：[钱包查询](C:/Users/Administrator/Documents/Codex/2026-09-25/quefa-multi-merchant-platform/outputs/quefa-open-platform/src/operations/wallet.ts:14)、[入账方法](C:/Users/Administrator/Documents/Codex/2026-09-25/quefa-multi-merchant-platform/outputs/quefa-open-platform/src/operations/wallet.ts:324)。

### 退款结果未知缺少独立恢复流程

当前退款批准后先写为 `processing`，再调用渠道。进程在渠道成功与本地入账之间中断，可能留下长期处理中记录；网络异常则可能被直接标成失败，但渠道实际可能已经退款。

已有退款请求号应继续复用，不能每次失败另建退款。需要“查询原退款结果”的任务、处理租约和补偿机制；未知结果保持核对中并保留额度占用，直到明确成功或明确未执行。退款确认、订单累计、账本、钱包冲正和通知事件应协调落账。

依据：[退款执行](C:/Users/Administrator/Documents/Codex/2026-09-25/quefa-multi-merchant-platform/outputs/quefa-open-platform/src/modules/refund-service.ts:236)。

### 页面轮询与缓存相互抵消

工作台通用 GET 缓存为 30 秒，页面视图缓存为 60 秒。订单列表每 3 秒轮询虽然清理了请求缓存，但随后调用的渲染仍可能命中旧视图；充值弹窗的轮询则可能直接读到 GET 缓存。弹窗关闭后还应检查并清理对应计时器。

因此，用户看到的“卡”至少有一部分是状态陈旧，而不一定是请求真的没有完成。应让活动订单绕过缓存，直接更新对应行；页面退出和弹窗关闭时取消轮询。静态商品配置与活动交易状态不能使用同一缓存策略。

此次没有测量浏览器交互延迟或接口 P95，不能给出已经确认的性能倍数。应先修复上述确定的更新问题，再量测慢查询、网络等待与渲染开销。

### 后台任务共用串行执行通道

支付核对、钱包充值核对、CDK 发码、充值履约和 Webhook 在同一轮 Worker 中串行等待。一个慢请求会推迟其他业务。WebHook 一次领取 20 个任务、租约 60 秒，但逐个请求最长 5 秒，理论耗时可超过租约；后续增加多 Worker 时需要避免重复领取。

履约查询错误可以持续重试，但缺少按任务年龄升级的待办和清晰错误分类。未知状态应升级核查，不能用“超时自动失败”来解决积压。

### 运营与运维还有几个容易忽略的缺口

- 全平台钱包汇总和部分流水查询只筛选启用代理，可能隐藏停用代理仍存在的资金与历史。停用应阻止新交易，不应让历史财务消失。
- 财务看板部分退款数据归属订单付款日，适合按订单批次看收益，但不能冒充按实际收退款日期统计的现金流水。
- 有待确认退款时会锁住代理整体收益划转和提现，补差退款也可能触发。应按实际风险冻结相关订单额度，而非无差别锁住全部收益。
- 生产健康检查仍要求 `tibo.ink/workspace` 返回 404，实际入口返回 200，日志已显示连续误报失败。需修正断言，并增加 Worker 心跳和积压监控。
- 每日备份服务确实先备份生产 SQLite，再备份 PostgreSQL。SQLite 使用在线备份并做完整性检查，不能说当前没业务备份；但定时恢复演练主要验证 PostgreSQL，尚不能证明实际业务 SQLite 可以完整恢复。此次也未验证异地副本和密钥恢复链路。

## 充值异常的目标流程

以下是拟实施规则，不是对现有 API 字段的承诺。

| 核实到的事实 | 用户提示与动作 | 系统处理 |
|---|---|---|
| 表单本地校验未通过且尚未创建任务 | 显示具体字段问题，允许修正 | 不派发、不消耗新权益，不称为取消任务 |
| 上游排队或处理中 | 正在充值，无取消或重提按钮 | 查原任务，展示最近核对时间 |
| 请求超时或结果未知 | 正在核对原任务，请勿重复提交 | 保留幂等引用，继续查询；超出内部时限生成核查待办 |
| 上游明确失败且确认终结 | 展示可理解的失败原因及重新提交入口 | 保留失败尝试；核实订单权益、退款占用和并发锁后允许新尝试 |
| 上游明确成功 | 充值成功 | 确认履约，按统一规则记账并通知 |
| 回调与查询矛盾或终态反转 | 正在核查，无重提按钮 | 记录冲突，暂停进一步履约或退款，生成管理员待办 |

“自动取消”在业务展示上可以理解为结束失败任务，但底层宜保留 `failed` 和失败依据，不要改成仿佛用户主动取消。订单仍可保持已付款、待重新提交，不自动创建新订单或重复扣供货款。

建议由服务端统一计算 `can_resubmit`、禁止原因及 `next_action`。客户端只负责展示，POST 重新提交时后端再次校验，不能只相信页面按钮或之前读到的状态。

可重提必须同时满足：上一次任务有可信的上游失败终态，没有仍在执行的尝试，订单权益尚可使用，没有已完成履约、全额业务退款或相冲突的退款占用。这些是系统一致性检查，不是新增人工审批。

为每次尝试保存失败来源、供应商任务引用、终态确认时间、证据摘要和最后核对时间。不得仅通过“服务不可用”等错误文案判断上游失败；HTTP 500、网络错误、人工核对状态均不算终态证据。

旧版本的 `agent_cancelled` 与 `cancelled` 保留历史读取兼容，停止产生不安全的新记录。迁移时先核对旧失败任务来源，不能把所有历史 `failed` 批量视为可重提。

来自京东式流程的可取之处是：告诉用户现在在哪一步、是否需要操作、系统接下来做什么，以及历史发生过什么。当前上游是否支持用户验证链接、3DS 等能力，需要按真实接口确认；不能仅为模仿页面而编造验证入口或保证完成时间。

## 单管理员的工单与任务体系

保留现有工单和消息模型，在上面补充业务关联与处理规则，不额外建设多人审批系统。

三种记录各自承担不同职责：订单记录买了什么及履约权益；工单记录一件问题的沟通和最终处理结论；任务记录下一步需要系统或管理员做什么。系统查询一次上游不是一张新工单，重试十次也不应发送十封邮件。

建议工单增加问题分类、优先级、关联订单与尝试、相关退款或提现、下一处理时限、等待对象、处理结果码。现有内部备注继续与代理可见消息隔离，敏感 Session 和密钥不得粘进工单或普通日志。

推荐状态为待处理、处理中、等待代理补充、等待上游、等待资金确认、已解决、已关闭。系统能通过回调明确解决的问题可以自动解决；人工关闭资金类工单必须满足退款成功、已核实打款等实际条件，不能仅靠点击“已解决”掩盖业务未完成。

异常自动生成规则：

- 同一订单同一次尝试同一问题类型只创建一张活跃工单；后续查询结果追加事件，不重复建单。
- 结果未知超过内部处理时限、上游长期无进展、退款结果待核实、Webhook 重试耗尽、财务差异，分别进入管理员待办。
- 输入不完整和可直接修正的问题，优先给代理明确反馈，不把全部表单错误都变成你的待办。
- 代理补充资料后自动回到待处理；上游恢复后，自动更新工单、相关任务和通知状态。
- 不设置不存在的主管或第二审核人。超时升级是提高你待办的优先级和提醒频率，不是层层转交。

订单详情应同时显示付款、CDK 权益、每次履约、退款、佣金、关联工单和通知时间线；工单详情可以直接打开这些证据，避免你在多个页面人工拼接事实。

## 邮件通知的范围与实现

建议加入，但以站内待办和业务状态为主，邮件作为送达渠道。当前商户与后台账户模型缺少完整的通知邮箱、验证状态和偏好设置，不能只接一个 SMTP 发送函数就认为完成。

| 事件 | 收件人 | 内容与动作 |
|---|---|---|
| 上游明确失败并允许重提 | 对应代理业务联系人 | 订单摘要、脱敏原因、回到代理后台或代理自有入口 |
| 需要补充资料或管理员回复工单 | 对应代理联系人 | 需要补什么、工单入口，不附敏感凭据 |
| 结果未知超时或上游长期异常 | 唯一平台管理员 | 影响范围、最后状态、待核查任务入口 |
| 退款结果未知或对账差异 | 管理员；必要时代理财务联系人 | 区分处理中与已退，不提前声称到账 |
| 提现、调账已完成 | 对应代理财务联系人 | 变动金额、币种、原因和余额流水入口 |
| Webhook 多次失败 | 代理技术联系人及管理员 | 事件类型、脱敏错误、重放入口 |
| 备份或恢复演练失败 | 管理员 | 哪一项失败及处理入口 |

代理默认使用已验证的主联系人邮箱，业务、财务和技术收件人可后续单独配置；不要让初始接入必须填一大堆联系人。平台只有你一个管理员，平台通知默认发给你。

终端客户的邮件默认由代理商自己的系统发送。平台通过 Webhook 提供事件与下一步动作，代理自行决定品牌、模板、发件人和客户入口。若将来允许平台代发，再单独实现代理域名验证、发信授权和品牌模板；不能从用户 Session 中擅自提取邮箱并作为订阅地址。

技术上采用事务事件与通知发件箱：业务成功落库后记录待投递事件，邮件 Worker 异步发送；失败重试、退信记录和最终失败进入通知中心。邮件失败不回滚付款或充值，也不阻塞履约线程。

按事件、收件人和模板版本去重。同一上游故障影响大量订单时，对管理员汇总告警，代理仅收到与自身相关的状态通知。只有状态变化、需要行动或超期提醒才发送，不能每次轮询都发。

邮件不得包含 Session、访问令牌、API 密钥、卡号或自动直充所用明文 CDK。资金操作链接必须登录后查看并确认，不允许打开邮件链接就执行退款、调账或提现。

## 手动增减代理余额

支持单管理员直接操作，但通过新增调账流水完成，不能把余额字段当成可随意覆盖的数字。

拟增加“财务 → 代理钱包 → 手动调账”弹窗，显示代理名称及编号、币种、目标钱包、当前余额、增加或减少、金额、变动后余额、必填原因、关联订单或工单。提交前在同一弹窗清楚确认一次，不需要另一人审批。

目标钱包应明确区分采购余额和收益余额。冻结余额只能由对应提现、退款或风险占用流程释放，不提供直接修改冻结数字的入口。若系统纠错导致应追偿额度超过可用余额，应明确记录待抵扣债务并限制新增支出，不能把已经支付出去的钱伪装成仍可直接扣除。

每笔调账至少记录唯一编号、幂等键、代理、钱包、币种、正负金额、前后余额、原因分类、详细说明、业务引用、操作者、操作时间。余额读取、限额校验、流水插入及审计记录需要在同一事务内完成，防止与下单、提现并发造成透支。

记错的调账通过关联原调账的反向流水更正，不修改或删除原流水。退款问题优先修复退款事实与自动冲正，不能先自动退款再手动加余额，造成双重补偿。

手动加余额不是支付宝到账，不增加真实收款统计；减少余额不是渠道退款，不应伪造出款。普通余额纠错也不自动计入佣金、销售额或充值奖励。线下真实到账补记应使用已有核实到账流程，并保存唯一渠道凭证。

界面按业务币种显示金额，不暴露“整数分”给操作者；底层仍使用最小货币单位整数，接口遵循统一金额格式。人民币与美元或 USDT 不混算，不能仅把单位文字改成 U。

## 财务与佣金的统一口径

先保留并明确两类交易：平台代收时，客户资金进入平台，再计算代理销售差价；代理自收款时，平台扣代理采购余额，平台账上的 paid 只表示供货款已支付，不能宣称终端客户已经向代理付款，也不重复生成平台代收佣金。

当前订单口径应成为钱包和账单的共同规则：普通退款影响代理差价；平台承担的补差不扣代理差价。是否达到可入账条件与应该入账多少必须分开计算，不能通过“有任何普通退款就丧失全部资格”代替退款金额计算。

以售价 135、供货价 110 为例：无退款佣金 25；平台补差 10 后仍为 25；普通退款 10 后为 15；全额普通退款后为 0。佣金已提现时，后续冲回通过债务或未来收益抵扣反映，不改已经完成的提现记录。纯补差退满等边界要按退款责任归属处理，不能仅按 paymentStatus 一刀切。

佣金释放时间需要明确为商品的交付义务：当前钱包倾向于真实充值成功后释放，即使只交付 CDK 也可能要等最终兑换。是否改为 CDK 交付即可确认，不属于本轮已经确定的规则，后续应单独明确并版本化，不能暗中提前或推迟结算。

建议统一为“佣金台账 → 收益钱包 → 提现”，结算单是周期对账快照，不再成为另一条独立重复入账路径。每笔记账有来源事件和唯一键；每天重算余额与投影比对，发现差异生成待办，不静默覆盖。

财务后台分别提供：按事件发生日的实际收款退款流水、按订单批次的收益分析、代理钱包、佣金与提现、对账差异、人工调账。停用代理仍出现在历史账与存量余额里。

退款需区分客户现金退款、采购余额退回、平台补差和佣金回冲。各自有金额、状态、责任归属与来源关联；不能仅用一列“已退款”概括全部资金动作。

## 后台结构与架构演进

建议保持模块化单体，不为当前规模拆微服务。先稳定交易规则和查询边界，再逐步整理代码与存储。

管理员后台默认进入待办台，重点为异常充值、待核实退款、提现、余额差异和告警；其余模块为订单与履约、售后工单、财务、代理与商品、接入与通知、系统设置。代理后台保留采购、订单、钱包、售后和开发接入，不把管理员当成某个默认代理来展示数据。

短表单使用弹窗，例如调账、商品启停和回复；需要多条证据的订单与工单使用独立详情页或带固定操作区的侧栏。不要把整个后台所有内容都塞进弹窗。邮件和通知需要可定位到具体订单或工单的稳定 URL，刷新和返回不丢位置。

工作台大模板拆为页面、共享组件、请求层与状态展示规则。GET 查询保持纯读取；活动订单更新对应行，列表按服务端分页、筛选与排序；概览不要用“最近 50 条”代表全量业务指标。

后端明确订单、履约、退款、钱包、工单、通知等模块的写入责任，以事务事件衔接。支付核对、充值履约、Webhook 和邮件分开调度，设置独立并发、租约续期、退避、失败分类和人工恢复入口。日志至少能定位业务对象和任务类型，但不能直接打印 SDK 原始请求与敏感数据。

SQLite 当前数据量很小，不能把所有卡顿都归咎于数据库。不过同步 JSON 存储、全量列表扫描和不必要的写事务会限制后续规模。需要先记录查询耗时与锁等待，再补分页和索引；迁移 PostgreSQL 时实现真正的仓储适配、唯一约束和事务，不能只切环境变量。

迁移采用隔离副本校验、影子读取对账、短暂停写切换与明确回退点；保持一个权威写库，避免没有补偿设计的双写。日志、数据库、配置密钥分别备份，做从 SQLite 业务备份恢复并核对订单与钱包的演练。

## 代理商开发文档的稳定交付

以实际可调用的接口契约为单一来源，维护版本、变更记录和废弃周期。修复路径前缀后，再生成示例或 SDK；文档与已发布接口共同验收，而不是只检查 YAML 能解析。

开发文档应覆盖完整场景：

1. 两种收款模式和金额归属，订单、付款、履约、退款分别代表什么。
2. 签名原文、金额格式、时间、幂等、超时后如何查询原订单，避免盲目重发。
3. CDK 交付与基于 CDK 的自动直充；自动直充不把明文 CDK 返回给终端客户。
4. 充值预检、每次尝试历史、上游明确失败后的原订单重提，以及结果未知时禁止重提。
5. 代理自建品牌入口如何根据 next_action 显示补资料、处理中、核对中、重提或联系售后。
6. Webhook 验签、重复、乱序、重试、补查和投递重放；只承诺确实发布的事件。
7. 工单、退款、采购余额、佣金与提现的查询与权限范围，代理不能使用平台调账能力。
8. 沙箱异常样例、稳定错误码、request_id 排障和上线清单。

拟增加的 `can_resubmit`、`next_action`、终态证据与售后接口，必须先实现和验证后才加入正式契约。当前已有字段与历史枚举保持兼容，新增字段优先采用向后兼容方式。

契约验证不仅覆盖成功路径，还应覆盖超时但上游已受理、延迟回调、重复回调、明确失败后重提、退款结果未知、佣金部分回冲和跨租户访问。不得用真实扣款测试替代可控契约与故障场景验证。

## 分阶段实施与验收

### 第一阶段先消除交易一致性风险

- 禁止代理主动取消，统一服务端重提资格，保留并核对历史失败记录。
- 修复普通部分退款与补差退款的佣金口径，移除 GET 写账，把成功事件与补偿入账统一。
- 完善退款结果未知的查询恢复与额度占用，防止重复退款或永远卡住。
- 修复活动订单缓存和轮询生命周期，修正健康检查的旧入口断言。

验收重点：运行中无取消权限；本地超时不能重提；上游明确失败才按权益开放；旧任务迟到回调不被悄悄吞掉；查询页面不会产生新资金流水；金额示例与钱包、订单、台账一致。发现历史差异时先生成逐单清单，再决定补正，不自动批量改钱。

### 第二阶段建立单人可处理的售后闭环

- 订单详情整合全部证据，异常自动生成去重工单和待办。
- 实现单管理员手动增减余额及反向冲正。
- 建立已验证通知邮箱、站内通知、邮件发件箱和按责任人发送的模板。
- 退款、提现、调账与工单关联，业务完成才关闭对应资金待办。

验收重点：重复提交调账不会重复变动；调账不伪造收款或佣金；代理只能看到自己的通知与工单；邮件失败不影响交易；一个异常不会反复建单或刷屏；单管理员无需第二人审核即可处理完整流程。

### 第三阶段稳定对外接入和持续运营

- 同步 API、文档、金额口径、事件列表与版本变更记录。
- 分离 Worker 队列，完善重试、任务心跳、积压、对账与通知投递指标。
- 完成真实业务库恢复演练和异地备份核验；根据测量结果推进数据库与前端拆分。

验收重点：按文档可完成从下单到异常恢复的全流程；生成客户端不出现重复路径；Webhook 消费可幂等恢复；真实业务备份恢复后订单、钱包、退款和待处理任务一致。性能目标应在采集基线后设定，不承诺未经测量的提升倍数。

## 后续仍需明确的业务选择

已确定的单管理员、禁止代理主动取消、上游明确失败才重提、代理自有品牌和平台承担补差，不需要再次确认。

后续实施只需补充实际邮件发送域名与已验证收件邮箱，以及纯 CDK 商品的佣金确认时点。它们不阻碍先处理第一阶段的确定性问题。邮件服务的凭证通过安全配置注入，不写入本报告或公开开发文档。
