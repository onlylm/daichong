# 支付与退款 Worker 有界队列

日期：2026-10-01（北京时间）  
状态：本地重构分支已完成并通过自动化测试，尚未部署生产。

## 问题

Worker 每秒轮询多个独立任务通道。原实现中，以下通道会先读取整类历史记录，再用 JavaScript 找一条到期记录：

- 平台零售支付宝订单；
- 代理采购钱包支付宝充值；
- 开票补差价支付宝支付；
- USDT 支付；
- 支付宝退款结果恢复。

订单和支付记录增加后，即使没有待处理任务，周期性全量读取也会持续占用 SQLite、JSON 解码和 Node.js 事件循环。

## 当前实现

### 支付队列

- 零售支付宝：SQLite 联结订单与支付尝试，只返回一笔支付状态仍为待支付且已到核对时间的订单。
- 钱包支付宝：按支付渠道、状态和下次核对时间读取一笔到期充值单。
- 开票补差价：按状态和下次核对时间读取一笔到期支付单；同一开票申请恢复支付入口时，也只查最新一笔待支付记录。
- USDT：每轮最多读取 20 笔到期且租约可用的候选，再一次批量读取关联订单，选择仍为待支付的订单；不再全表排序或逐笔读取订单。

### 退款队列

- SQLite 联结退款、原订单和支付尝试，只返回一笔到期且原支付渠道为支付宝的处理中退款。
- 管理员按退款编号审核、驳回时，SQLite 直接按全局主键读取退款，不再遍历全部订单及其退款。

新增通用查询条件 `lte_or_null`，表达“下次核对时间为空，或已经到期”。内存仓储继续作为隔离测试回退；生产 SQLite 使用状态/渠道/到期时间索引和有界查询。

## 安全边界

- 本轮只改变候选任务的读取方式，不改变支付确认、签名验证、金额绑定、租约、退款幂等号和状态机。
- 查询不到任务即结束本轮，不会创建新订单、重新付款或重新退款。
- 退款恢复继续复用原退款编号和原金额；结果未知时保留处理中，不生成第二笔退款。
- 支付成功仍必须经过渠道签名、商户身份、订单号和金额校验，浏览器返回参数不能标记到账。
- 全局资金流水防重没有被截断；后续只能用唯一约束或精确索引替代，不能按前若干条近似判断。

## 自动化验证

新增回归构造“未来才到期”和“当前已到期”两组记录，确认：

- 开票、钱包和 USDT Worker 只选择当前已到期任务；
- 零售支付宝通过订单/支付联结选择正确订单；
- 支付队列不调用 `listOperations` 全量读取；
- 退款队列能按渠道和到期时间精确命中；
- 能按退款主键直接读取原退款。

最终结果以 `npm run check` 为准。本轮不部署生产，也不调用真实支付宝或 USDT 服务。
