# 成本核算列表服务端分页

日期：2026-10-01（北京时间）  
状态：本地重构分支已完成并通过自动化测试，尚未部署生产。

## 改造原因

原 `/workspace/api/finance/costs` 会一次读取全部订单、履约记录、成本记录、补差付款和代理商，再在服务层筛选并截取最近 200 条。数据增长后，即使页面只显示少量记录，也会持续增加 SQLite 查询、JSON 解码和 Node.js 事件循环占用。

## 当前实现

- 接口支持 `page`、`limit`、`status` 和 `search`。
- `status` 可取 `all`、`pending_review`、`confirmed`、`disputed`。
- `search` 匹配平台订单号、代理订单号、代理名称和代理编号。
- SQLite 在数据库内判断“已有成本记录，或存在成功履约”，同时完成状态筛选、总数统计、排序和分页。
- 已归档订单和联调测试订单不进入运营成本列表。
- 列表页每页默认 20 条；只读取当前页对应的成本摘要，不读取补差付款明细。
- 打开订单详情时才读取完整成本凭证、上游交易匹配结果和补差付款记录。

列表中的订单号与“核算详情”均可打开同一订单详情抽屉。筛选、搜索和翻页会保留在成本子页面内，不触发其他资金分区的数据读取。

## 查询边界

SQLite 的一页成本记录固定为三次有界查询：

1. 统计符合条件的记录总数；
2. 读取当前页订单和代理名称；
3. 批量读取当前页订单对应的成本摘要。

查询次数不会随历史订单总数逐单增长。新增 `(kind, status, orderId)` 表达式索引，用于状态与订单关联查询。内存仓储仅用于隔离测试，保留等价的应用层回退逻辑。

## 安全与资金规则

- 列表读取不修改订单、余额、佣金、退款或补差状态。
- 退差基准、真实美元成本和补差付款仍是独立记录。
- 列表分页不能替代全局资金防重；付款流水、清算凭证和请求号仍保持全局唯一校验。
- 核算、登记真实付款、确认客户到账仍是三个独立人工动作，系统不会因打开或筛选列表自动退款、转账或打款。

## 自动化验证

新增接口回归覆盖：

- 7 笔成功履约订单的第二页读取；
- 待核验与已确认状态筛选；
- 按代理订单号搜索；
- 分页总数、页数和页大小；
- SQLite 专用分页方法确实被调用；
- 成本列表固定为三次数据库查询，且不逐单调用履约查询。

本地最终结果以 `npm run check` 为准。浏览器桌面、手机和键盘交互由用户按既定安排自行验收；本轮不部署生产。
