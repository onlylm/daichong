## 1. 生产采样与结论边界

2026-09-30 北京时间 14:04，在生产 API 容器内，对生产 SQLite 的只读事务快照调用现有读取服务。样本含 20 个商户、77 笔订单、32 条履约、31 条 CDK 记录、36 条钱包流水。每项调用三次；没有调用付款、退款、充值、入佣或数据修复方法。

| 服务读取 | 三次耗时范围 | 每次 SQL 数 | 每次累计返回数据库记录数 |
|---|---|---|---|
| 全代理订单列表，第一页 20 条，无搜索 | 176.38–207.21ms | 137 | 2,436 |
| 代理钱包总览 | 39.19–46.59ms | 114 | 789 |
| 最近 7 日平台财务汇总 | 54.78–82.41ms | 43 | 946 |
| 抽样一笔订单详情 | 5.77–8.64ms | 6 | 158 |

“累计返回记录数”包含重复读取，不是不同业务记录的数量。计时含 SQL 准备、JSON 解码和服务计算，未覆盖 HTTP 鉴权、反向代理、浏览器网络、DOM 渲染和真实并发；三次采样不能推导 P95。钱包读取采样复用外层只读快照，未执行生产钱包服务的写锁事务。

单笔详情在小数据量下读取较快，但列表仅返回 20 行却执行 137 次 SQL，已证明存在读放大。同步 SQLite 和同步 JSON 解码还会占用 API 进程事件循环；数据增长后可能拖慢同进程的其他请求，具体影响须压测验证。

## 2. 已有能力与当前问题

### 2.1 已有能力需要保留

- `src/operations/workspace-page.ts` 的 `showViewPane` 已进行本地页面显隐。
- `openOrderDetailModal` 已先创建并打开弹窗，再查询数据。
- `render` 已有 `AbortController` 和 `epoch`，避免旧页面请求覆盖新页面。
- 订单轮询已检查当前页面和 `document.hidden`，隐藏页面不发起这一轮查询。
- 订单详情从本地仓储读取，没有在普通详情中同步调用上游或支付宝。
- 钱包读取已与自动入佣分离。优化时不得重新把资金变更放入 GET。

### 2.2 实时查询误清空全局缓存

`api()` 将订单、钱包、财务、工单、商品、供应与支付路径归为实时资源。非缓存请求成功后执行 `responseCache.clear()` 和 `viewLoadedAt.clear()`，因此实时 GET 也会清掉其他页面已加载标记。实时 GET 同时不参与现有 `inflight` 合并。

改造时将三个概念拆开：是否复用已有读取结果、是否合并正在进行的读取、哪些成功写入需要失效哪些缓存。实时查询可以不使用旧结果，但仍应合并相同租户和查询条件的并发读取。成功 GET 不应全局失效；写入按订单、钱包、商品、权限等资源定向失效。

### 2.3 订单每轮刷新重复取列表

`syncOrdersLive()` 先请求 `/orders`，随后调用 `render({silent:true,force:true})`；`orders()` 又请求 `/orders`。重绘时还会经过代理目录、商品选项读取。定时器没有自身的单次执行保护，慢请求时存在重叠风险。

改为每轮只读一次当前列表，将结果直接更新已挂载的行、汇总和状态。代理目录、商品名称等配置按版本复用。同一列表只允许一个在途刷新；编辑弹窗打开时避免重建背景列表，失败采用退避。后台刷新保留筛选、页码、滚动和焦点。

### 2.4 财务子页切换仍加载所有分区

`wallet()` 每次无论选择“平台对账”“代理钱包”还是“退款审核”，都会并行读取钱包总览、流水和财务汇总；有审核权限时再加两类退款队列。子页按钮调用整体 `render`，所以仅切一个标签也会重复请求全部数据。

改为子面板立即显隐并保留最近成功数据。平台对账只取财务汇总，代理钱包取余额和当前页流水，退款审核取待审队列。代理钱包详情的充值、提现、流水也按标签读取和分页，避免一次构建三个表格后只显示一个。汇总卡与列表可以独立刷新，不必相互等待。

### 2.5 订单弹窗内容还受第二次请求阻塞

管理员打开详情后先读取订单，符合条件时再串行调用 `/orders/{id}/platform-trace`，取得上游凭证后才替换整个弹窗内容。上游凭证读取是权限受控、解密并写审计的敏感操作，不应作为普通详情首屏的前置条件。

首帧使用列表已有的单号、金额、状态和时间。详情返回即填充首屏；上游凭证改为管理员显式点击后按需读取，继续保持专属权限、审计和 `no-store`。关闭弹窗取消请求，加载失败提供行内重试并保留弹窗可关闭；历史审计可展开后分页读取。

### 2.6 仓储全量读取后在内存分页

`listWorkspaceOrders` 先读全部租户订单，再逐单读取履约、筛选、排序和分页；即使状态为 `all` 也先读取履约。搜索增加逐单 CDK 和履约读取，当前页生成时又再次读取。

`SqliteRepository.listFulfillments` 读取一个商户全部履约后按订单过滤；`findCdkVoucherByOrder` 读取全部商户 CDK 后查找。钱包总览按商户重复求和与检查待入佣订单，财务汇总全量遍历订单，退款队列也逐单扫描退款。

现有通用表索引包括主键、业务唯一键和 `(kind, merchant_id, updated_at)`，未解决 payload 内订单关联、业务时间和状态的索引查询。仅增加前端缓存不能消除这些扫描。

## 3. 分阶段改造任务

### 3.1 第一阶段 修正请求和页面更新

1. 实时 GET 参加在途请求合并，成功读取不清空全局缓存。
2. 订单每轮刷新只取一次列表，直接复用返回数据；增加单次执行、退避和弹窗编辑保护。
3. 财务子页按需请求，标签显隐立即响应；页码、筛选和滚动保留在分区状态中。
4. 订单页配置读取与列表读取解除串行依赖。使用有限聚合或并行读取，避免启动时加载所有页面。
5. 详情首屏先填充，敏感凭证按需读取；弹窗增加取消、重试和焦点返回。

读取缓存建议按资源设短 TTL 和配置版本，键包含账号、角色权限版本、租户、资源、筛选和分页。管理员全平台查询与代理单租户查询必须分开。旧余额可展示并标注更新时间，扣款、退款、提现和调账仍以服务端事务内核验为准。

### 3.2 第二阶段 将筛选分页和关联下推数据库

1. 增加按租户、筛选条件、排序、游标查询订单的方法，不再先返回全部订单。
2. 当前页订单的履约、支付和 CDK 摘要批量读取，或使用结构化关联查询。
3. 增加订单关联读取方法，移除单笔查询时的商户全量和全平台扫描。
4. 汇总查询直接聚合。钱包余额可维护可重建的读取投影，但权威依据仍是资金流水和事务。
5. 普通读取使用读取快照，避免无资金变更的查询申请 `BEGIN IMMEDIATE` 写锁。

短期可为 JSON 表增加经过验证的提取列或表达式索引，并让 SQL 使用相同表达式；应同时下推 WHERE、排序和 LIMIT，单独建索引但仍全量解析 JSON 不会解决问题。长期采用结构化订单、履约、退款、钱包流水和审计表。

建议索引与查询匹配：订单按租户和创建时间，履约按租户和订单号，CDK 按租户和订单号，钱包流水按租户和创建时间，退款按租户和订单号及状态。时间排序使用业务 `created_at`，不要用因状态更新而变化的 `updated_at` 替代订单创建时间。

PostgreSQL 迁移必须实现仓储、事务、唯一约束和隔离校验，并对资金读取做影子核对。项目有迁移文件、服务器有 PostgreSQL/Redis，不代表当前业务已经使用它们。当前不需要为了页面交互直接改成微服务或重写框架。

### 3.3 第三阶段 完善进度同步和异常处理

代理商必须持续获得充值进度、可公开的失败原因和明确的下一步操作。2026-09-30 16:38 已部署统一公开阶段、进度版本/时间、阶段变化 Outbox 事件，以及管理员取消未派发任务后的退款/重提分流。查询和重提规则见对外文档第 7.4 节。下表保留整体目标，售后关联与后台性能改造尚未全部实现。

| 待改造项 | 目标行为 |
|---|---|
| 安全业务进度 | 所有代理默认获得统一的公开阶段及阶段说明；内部用卡、上游身份和真实费用继续独立授权 |
| 失败反馈 | 返回稳定失败码、安全原因和操作指引，区分资料问题、确定失败、结果未知和需平台处理 |
| 进度版本 | 同一尝试的对外状态变化递增版本，附状态更新时间；用于重复和乱序通知处理 |
| 进度事件 | 新增并正式发布 `fulfillment.updated`，重要阶段变化才投递；不按每次上游查询重复通知 |
| 恢复入口 | 最近尝试明确失败且允许重提时，提供恢复条件；代理商使用自己的品牌订单链接开放输入入口 |
| 查询兜底 | Webhook 失败、浏览器刷新和换设备后，查询接口能恢复同一订单当前尝试 |
| 售后关联 | 异常关联平台任务和工单，代理商可看到公共处理状态和处理结果 |

进度事件须在状态持久化的同一事务中写 Outbox，使用“任务号加对外版本”去重，沿用现有投递签名、重试和租户权限。正常阶段更新不逐条发邮件；需要客户补充资料、最终失败或工单公共回复时，按通知偏好发邮件。邮件和 Webhook 都不能包含 Session、密码、完整卡号、上游原始 CDK 或内部排障日志。

后台可显示更多内部依据，但代理商 API、代理工作台和 Webhook 必须共用公开字段转换。管理员修改可见性后，读取缓存必须失效。失败码和进度不能依赖解析自由文本，避免文案变化使代理商程序判断错误。

### 3.4 本轮已实现：管理员取消后的分流

管理员在订单详情的「人工审核与订单动作」中点击「取消 / 处理充值」，选择处理方式并填写原因。仅当前最新且确认未派发的任务、或上游已经明确失败/确认取消的任务可处理；已成功、已派发但结果未知、旧尝试、已退款及正在退款的订单不能绕过保护。

- **允许重新提交**：结束确认未派发的任务，或使用已确认安全结束的失败/取消结果，开放原订单的新尝试。保留原付款和原采购记录，不再次收款；可复用的 CDK 资源回到未使用状态。客户在代理自己的网站修正资料后重提，代理使用新的幂等键，仍查询原订单。
- **退款**：关闭重提入口，锁定原充值资源。平台代收订单创建原路退款申请，并由同一管理员在本次操作中调用现有退款执行接口；不需要其他人员核验。代理自收订单只退回代理采购余额，不调用平台的客户支付宝退款，零售款由代理自己的渠道退给客户。

内部接口为 `POST /workspace/api/orders/{id}/recharge/resolve`，要求平台登录、CSRF 和相应权限，输入 `fulfillmentId/action/reason/requestKey/confirmCancel`，`action=retry|refund`、`confirmCancel=true`。此接口不对代理 Partner API 开放。取消、恢复选择、退款申请或采购账本变更以及通知入库在同一事务中完成，同处理号同请求可重放，不同请求冲突；外部原路退款通过既有审批执行接口在事务提交之后调用，超时保留原退款单核对，不能再申请另一笔。

履约记录内部保存 `recoveryAction/recoveryReason`；对外只返回 `recovery_action`，不暴露内部处理原因、凭据或上游 CDK。选择变化通过 `fulfillment.updated` 通知代理；退款完成继续使用 `refund.succeeded` 或 `procurement.refunded`。代理收到通知后应查询最新订单与任务，不能凭旧事件重新开放入口。

## 4. 代理商反馈的业务规则

充值流程必须区分付款、交付资源就绪、充值受理、处理中、结果待确认、成功、明确失败和售后处理中。HTTP 202 只说明任务被接受，付款成功只说明资金被确认，两者都不是充值成功。

`queued/running` 及 `review/pending/requires_action/plus_paid` 等中间业务结果不得显示成最终失败。网络超时显示“进度暂未更新，正在核对原任务”，保留已知进度；不能自动取消或另建任务。

只有最近尝试已明确失败、安全结束且 `retry_allowed=true`，才能让客户修正资料后在原订单重提。自动直充的恢复入口还要检查 `fallback_recharge_available=true`。入口地址由代理商自己生成和鉴权，不向客户交付 CDK，也不要求跳转平台品牌页面。

进度只能展示已经确认的阶段。上游没有细分阶段时显示“排队中”或“处理中”，不编造百分比、完成时间或推测已经完成的步骤。失败页面至少显示原因、本站订单号和可用动作；代理后台另显示平台订单号、任务号和请求号方便排障。
