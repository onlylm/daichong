# 现有 Quefa 系统只读审阅记录

版本：v0.2（2026-09-26）  
用途：记录本次新平台设计所参考的成熟口径，不作为生产配置或迁移清单。

## 审阅边界

- 只读参考目录：`merchant-gateway` 的公开文档、TypeScript 源码、测试与示例商品配置。
- 未读取生产 `.env`、运行数据库、日志、密钥、支付宝私钥、上游密钥或真实 Session。
- 未修改原项目，未发起真实支付、退款、履约、回调或部署。
- 新平台不复制数据库、不迁移密钥、不复用域名；仅复用经过验证的业务语义。

## 已验证的公开链路

现有单商户模式中的外部“平台”本质上是推广/销售渠道：它传商品、终端售价和自己的订单号，Quefa 校验供货价与售价范围；Quefa 自己调用支付宝电脑网站支付接口生成二维码、接收支付宝回调、主动查单并执行退款。买家资金进入 Quefa，外部平台不提供支付宝账户或密钥。

1. 拉取商品目录并校验供货价、最高销售价和数量。
2. 使用商户订单号幂等开单，返回支付宝二维码及过期时间。
3. 支付宝异步通知验签后再次主动查单；浏览器跳转不作为到账依据。
4. 已支付订单提交 Session，立即返回受理状态，由后台任务履约。
5. 履约按 `preview → preflight → redeem → result` 推进；一旦提交 `redeem`，结果未知时只查询 `result`，绝不重复兑换。
6. 退款接口仅登记申请并锁定履约，运营审核后才实际原路退款。
7. `order.paid`、`order.refunded` 经 Outbox 投递，回调失败按退避计划重试。
8. Session 与兑换码采用 AES-256-GCM 加密，Session 在终态清除；日志对密钥和凭证脱敏。

## 原系统状态口径

| 对象 | 状态 |
|---|---|
| 支付 | `pending`、`paid`、`expired`、`refunded`、`closed` |
| 履约 | `submitting`、`queued`、`running`、`success`、`failed` |
| 退款 | `requested`、`processing`、`succeeded`、`failed`、`rejected` |
| 履约失败 | `session_invalid`、`account_has_subscription`、`region_unsupported`、`payment_blocked`、`verification_timeout`、`other` |

## 新平台保留与调整

保留：幂等开单、支付二次确认、结果未知不重复提交、退款人工审核、Session 加密和终态清理、Outbox 重试、失败原因标准化。

调整：

- API Key 升级为 `partner_id + key_id + client_secret` 的 HMAC-SHA256 签名。
- SQLite 单实例升级为 PostgreSQL，Redis 用于 Nonce、防重放、限流和短锁。
- 所有业务表强制 `merchant_id`，仓储查询必须携带租户条件，生产数据库启用 PostgreSQL RLS 作为第二道防线。
- 原系统“平台供货价/平台利润”改名为“Quefa 对代理商供货价/代理商销售差价”，并新增支付手续费、上游真实成本、Quefa 毛利、代理商待结算等不可变分录。
- 结算单封存后不回写；后续退款进入下一期冲正或负向调整。
- 支付宝能力保持 Quefa 平台级单一归属；多代理商化只扩展销售租户、价格、订单与结算隔离，不扩展代理商支付账户。

## 不允许复用的内容

- 原生产域名、数据库文件、数据库连接串、应用密钥、支付宝私钥/公钥配置、上游 API Key。
- 原 Session、CDK、用户邮箱明文、订单原始敏感响应。
- 原系统内部上游标识和 Quefa 支付配置不得出现在代理商 API、Webhook 或日志中。
