# 代理商沙箱联调指南

> 2026-10-01 更新：代理账号默认开放 API，无需申请或预存；主账号可直接创建服务端密钥。在隔离模拟库使用 `platform_collect` 完成联调，不把模拟入账当作真实资金。只有测试 `agent_collect` 时才需要模拟采购余额；生产采购余额必须以真实支付宝到账为准。自建兑换能力仍受代理配置与风控开关约束。详见第 15、16 份文档。

版本：v1（2026-09-26）。本指南用于模拟完整销售流程，不连接真实支付宝、真实上游或生产数据。

## 1. 已提供的沙箱能力

- 固定测试代理商凭证和商品授权；
- HMAC 鉴权、Nonce 防重放和请求幂等；
- 商品查询、订单创建/分页/详情；
- 代理后端直出并由代理页面本地展示的模拟支付宝付款码；
- 订单、支付尝试、履约、退款、幂等、Outbox 与 Webhook Delivery 的 SQLite 持久化；
- API 与 Worker 两个进程共享数据，服务重启后数据保留；
- 模拟履约 Worker；
- 代理品牌 CDK 签发/兑换与基于订单 CDK 的自动代充；
- 带 HMAC 签名、租约、失败退避和死信状态的 Webhook POST；
- 代理商商城前端、服务端签名代理和 Webhook 接收示例。

## 2. 测试凭证

默认值来自 `.env.example`，仅限本地沙箱：

```text
Base URL:       http://127.0.0.1:3200
partner_id:     pt_demo_a
key_id:         key_demo_a_01
client_secret:  replace-with-demo-secret-at-least-32-chars
webhook_secret: replace-demo-webhook-secret
```

把沙箱开放给外部代理商前必须为每家代理商重新生成独立凭证，不得继续使用这些公开默认值。

签发独立凭证（完整 secret 仅在本次输出）：

```powershell
npm run build
npm run sandbox:provision -- pt_agent01 "代理商一" "https://agent.example.com/webhooks/quefa"
```

若沙箱运行在 Docker 中：

```powershell
docker compose exec api node dist/cli/provision-sandbox-agent.js pt_agent01 "代理商一" "https://agent.example.com/webhooks/quefa"
```

命令同时登记该代理商的 Webhook、创建开放 API 应用并授权演示商品；重复 `partner_id` 会被拒绝，不会覆盖原凭证。

## 3. Docker 启动

```powershell
Copy-Item .env.example .env
docker compose up --build
```

默认只监听 `127.0.0.1:3200`。API 和 Worker 共享 `quefa_sandbox` 数据卷。确认就绪：

```powershell
Invoke-RestMethod http://127.0.0.1:3200/health/ready
```

预期 `storage` 为 `sqlite-sandbox`。

## 4. 启动代理商完整示例

另开终端：

```powershell
$env:PARTNER_DEMO_ALLOW_MOCK_PAY='true'
npm run demo:partner
```

打开 `http://127.0.0.1:3300`，依次执行：

1. 查看授权商品；
2. 创建 135 元订单；
3. 默认本机 Mock 环境点击代理页面内的“沙箱模拟付款”；接入支付宝沙箱时，代理后端改为调用 `/v1/orders/{order_id}/payment-code`，当前页面直接显示返回的本地二维码图片；
4. 确认模拟付款，不跳转或展示平台品牌页面；
5. 在代理商商城查询，状态应为 `paid`；
6. 在当前代理页面提交虚构测试 Session；
7. 代理后端调用 `mode=auto_recharge` 的 `/v1/redemptions`，平台内部用订单 CDK 兑换，不返回明文底层码；
8. Worker 将履约推进到 `succeeded`，代理页面通过安全状态接口或 Webhook 更新结果；
9. 刷新 Webhook，应收到 `order.paid`、`cdk.issued` 和自动直充对应的 `fulfillment.succeeded`。

示例源码位于 `examples/partner-demo/server.mjs`。浏览器只访问代理商示例服务，`client_secret` 只保留在服务端。

## 6. 订单与支付联调

当前完整示例不把 `qr_payload` 交给浏览器。接入支付宝沙箱时，代理后端创建订单后签名调用 `POST /v1/orders/{order_id}/payment-code`，将 `qr_image_data_url` 转交自己的页面本地显示。二维码金额和支付配置只取订单服务端快照，调用方不能临时改价。默认纯 Mock 环境没有支付宝付款码，必须显式设置 `PARTNER_DEMO_ALLOW_MOCK_PAY=true`，由代理后端调用仅存在于本机沙箱的模拟确认端点；生产环境不存在这个按钮和端点。代理商不得自行修改生产支付状态，也不需要配置平台支付宝密钥。

支付宝沙箱模式下，管理员须先为示例代理开启 `directPaymentCodeEnabled`。未开启时返回 `403 direct_payment_code_disabled`；不能因此改回把客户跳转平台页面的旧接法。付款结果仍以验签 Webhook 或 `GET /v1/orders/{order_id}` 为准。

订单列表：

```http
GET /v1/orders?payment_status=paid&limit=20&cursor=<上一页next_cursor>
```

订单详情：

```http
GET /v1/orders/{order_id}
```

当前四项套餐的 `fulfillment_mode` 固定为 `cdk`，下单时另选 `delivery_mode=cdk` 或 `delivery_mode=auto_recharge`。付款后 Worker 生成订单绑定的 CDK；前者交付代理品牌公开号，后者仅在平台内部使用该凭证自动兑换。代理商不会获得底层卡密；公开号必须当作不透明字符串。

## 7. Webhook 验收

Quefa 发送以下关键头：

```http
X-Quefa-Event: order.paid
X-Quefa-Event-Id: evt_...
X-Quefa-Delivery: dlv_...
X-Quefa-Timestamp: 1790380000
X-Quefa-Signature: t=1790380000,v1=<hex>
```

签名原文是 `timestamp + "." + 原始请求体字节`。接收方先验签和检查时间偏差，再以 `event_id` 做业务去重，持久化后快速返回 2xx。非 2xx、网络错误或超时会触发退避重试。

## 8. 让外部代理商访问

当前交付的是可部署沙箱包，不包含已经购买或配置好的公网域名。部署到独立沙箱服务器时必须：

1. 使用独立 HTTPS 域名和反向代理；
2. 把 `PUBLIC_BASE_URL` 改为该 HTTPS 域名；
3. 只开放 443，禁止直接暴露 SQLite 文件和 Worker；
4. 为每家代理商生成独立 `partner_id/key_id/client_secret/webhook_secret`；
5. 登记代理商 HTTPS Webhook 地址和出口 IP；
6. 开启访问日志脱敏、限流和防火墙；
7. 明确标注“模拟支付，不产生真实扣款”。

本地临时允许局域网访问时可以设置 `SANDBOX_BIND_IP=0.0.0.0`，但公开默认凭证下严禁暴露到互联网。

## 9. 数据与安全边界

- SQLite 文件只用于沙箱，会保存测试 API/Webhook secret，不允许放真实密钥；
- 只能提交虚构 Session，禁止使用真实用户 Session；
- `NODE_ENV=production` 会被程序主动拒绝；
- 真实充值适配器已经实现，但没有正式凭证时只能使用模拟模式；真实上线仍需 PostgreSQL/RLS、Redis/KMS、Quefa 自有支付宝适配器、固定出口 IP、备份恢复和安全验收。

如需清空 Docker 沙箱，`docker compose down -v` 会删除整个 `quefa_sandbox` 数据卷且不可恢复；执行前必须确认其中只有可丢弃的测试数据。
