# 部署与备份恢复手册

版本：v0.2。本文不包含任何真实密码、私钥、Session 或生产地址。代理商只接入 Quefa 开放 API，不提供任何支付宝配置。

## 1. 环境隔离

开发、沙箱、预生产、生产使用独立云账号/项目、VPC、域名、数据库、Redis、对象存储、KMS 主密钥、Quefa 自有支付应用和上游凭证。每个环境使用一套由 Quefa 管理的平台级支付配置，所有代理商共享该环境的集中支付能力，不允许按代理商上传支付宝账号、应用、证书或私钥。禁止从原 Quefa 生产环境复制 `.env`、数据库或密钥。生产管理员账号启用 MFA，人员按最小权限授权。

## 2. 基础设施

下列 PostgreSQL/多副本形态是扩容目标。当前单服务器低订单量生产运行时以 `deploy/production/README.md` 为准，应用主账本为 SQLite WAL；在 PostgreSQL Repository 完成业务等价迁移、RLS 和恢复验收前，不得把空置 PostgreSQL 备份当成应用账本备份。

- 反向代理/WAF：TLS 1.2+、HSTS、请求体限制、基础 DDoS/速率控制。
- API：至少 2 副本，无本地状态，滚动发布。
- Worker：至少 2 副本，使用数据库租约，支持优雅停止。
- PostgreSQL：托管主备、PITR、磁盘加密、私网访问、`sslmode=verify-full`。
- Redis：高可用、TLS、ACL、私网访问；仅放可重建的 Nonce/限流/短锁数据。
- Secret/KMS：密钥管理服务或 Secret Manager；应用环境变量只保存引用或短期凭证。
- 对象存储：备份与导出加密，版本控制、不可变保留、最小访问。

## 3. 发布流程

1. 变更评审，确认不含秘密与真实 Session。
2. CI 执行格式/类型检查、单元/集成/跨租户测试、依赖与镜像扫描。
3. 构建带 Git SHA 的不可变镜像并生成 SBOM。
4. 生产数据库做按需快照，确认最近自动备份可恢复。
5. 在独立迁移任务中执行向前兼容迁移；API/Worker 不自动抢跑迁移。
6. 先发布 API，再发布 Worker；或按迁移兼容计划分阶段。
7. 验证 `/health/live`、`/health/ready`，并确认本次发布启动的新 Worker 已写入新实例心跳、全部关键通道至少完成首轮且没有连续失败；旧实例遗留心跳不得作为发布成功证据。再验证签名、沙箱开单、Outbox、监控和日志脱敏。
8. 灰度观察错误率、队列深度、对账差异，再扩大流量。

数据库破坏性变更采用 Expand/Migrate/Contract：先加新列/表并双写，再回填与切读，最后在后续版本删除旧结构。禁止同一发布直接重命名/删除仍被旧代码使用的列。

## 4. 配置与密钥

`.env.example` 仅列变量名和安全占位符。生产 secret 通过 Secret Manager 注入。主密钥、代理商开放 API 密钥、Webhook 密钥、Quefa 支付/上游凭证分别轮换；不得共用。Quefa 支付凭证仅授予支付适配器和受控运维角色，代理商后台/API/导出均不可读。轮换前确认双钥/双版本解密兼容，轮换后保留可解密历史密文所需的旧 KMS 版本，直至数据清理或安全重加密。

## 5. 备份策略

- 当前 SQLite 主账本：每天使用 SQLite 在线备份 API/CLI 生成自包含快照，执行 `integrity_check`，保存 SHA-256 清单，本机滚动保留 14 天；每周对最新快照进行一次隔离恢复及逻辑摘要对比。
- PostgreSQL：每日全量快照 + 连续 WAL/PITR，保留 35 天；月度备份保留 12 个月（最终以法规/合同为准）。
- 配置：基础设施代码、迁移和非秘密配置进入版本库；Secret Manager 配置单独备份元数据与恢复流程。
- 对象存储：跨可用区复制、版本控制和对象锁；备份文件服务端加密。
- Redis：不作为业务恢复依据，可启用持久化以缩短恢复，但允许从数据库重建。
- 每份备份记录时间、范围、版本、校验和、加密密钥版本和到期日。

## 6. 恢复演练

至少每季度在隔离账户恢复：

1. 创建全新网络与数据库实例，不连接生产外部服务。
2. 恢复指定时间点数据库，使用独立恢复环境密钥和阻断出口策略。
3. 运行迁移校验、行数/总额校验、分录借贷平衡与租户隔离检查。
4. 重建余额投影和搜索索引；Redis 从空实例启动。
5. 将支付/上游/Webhook 客户端强制为 mock，防止恢复数据触发外部副作用。
6. 验证抽样订单时间轴、退款、结算与审计日志。
7. 记录实际 RPO/RTO、失败点和改进负责人。

当前 SQLite 自动演练由 `deploy/production/verify-backup-restore.sh` 执行。它只读备份文件，恢复到临时库并验证完整性、外键、JSON、结构摘要、全记录逻辑摘要、记录总数和分类数量，结束后删除临时库，完整报告写在原备份旁并保持 root `0600`。供后台健康卡读取的脱敏摘要单独发布到 `/opt/recharge-platform/monitoring/sqlite-restore-health.json`，属主继承生产数据库、权限为 `0640`，通过只读挂载进入容器。该演练不启动 API/Worker、不读取应用加密密钥、不调用支付、供应商或 Webhook，也绝不覆盖 `production.sqlite`。

本机每日快照最多只能提供约 24 小时 RPO，尚未满足架构目标中的 RPO ≤ 5 分钟；未完成异机加密复制、不可变保留和告警前，上线检查表的“备份/PITR”仍保持未通过。

## 7. 灾难恢复

事故负责人先冻结发布与高风险 Worker，保留证据，判断是否需要停用密钥。数据库故障优先使用托管故障转移；区域灾难按预演手册恢复到备用区域。切流前确认 DNS/TLS、固定出口 IP、Quefa 自有支付宝回调、上游白名单和 Secret 均为新环境值；代理商侧无需变更或提供支付宝配置。

恢复后不要直接放开 Worker：先只读核对支付/退款/履约未知状态，再按类型逐步启用查询型任务，最后启用会产生副作用的任务。所有补偿操作通过幂等业务号执行。

## 8. 回滚

应用回滚到前一不可变镜像；数据库迁移默认向前修复，只有经过验证且不会丢数据的迁移才允许 down。出现资金或租户隔离风险时立即停止相关入口/Worker，保存请求和审计证据，启动事件响应，不以删除记录“回滚”。

## 9. 代理商联调 Compose

本项目 `compose.yaml` 仅用于代理商联调沙箱，使用 mock 支付、mock 上游和 API/Worker 共享的 SQLite WAL 数据卷。示例口令不得用于任何联网环境。默认只绑定 `127.0.0.1:3200`；需要外部联调时应部署到隔离服务器并由 HTTPS 反向代理只开放 443，不能直接暴露 SQLite 文件、Worker 或示例密钥。详细步骤见 `docs/10-代理商沙箱联调指南.md`。

生产仍以 PostgreSQL、Redis、KMS 和独立 Worker 为目标架构；SQLite 沙箱不执行 PostgreSQL 迁移，不能用于真实资金、真实 Session 或生产部署。
