# Quefa 充值供应管理后台

版本：v0.1。本文只描述 Quefa 平台内部的充值供应配置。代理商和终端客户不会接触本后台、上游域名、API Key、供应订单号或原始 CDK。

## 能力边界

后台当前只包含以下能力：

- 保存并测试上游 OpenAPI/CDK 连接。
- 查询供应余额和可消费余额。
- 只同步 GPT 充值套餐及可售状态。
- 把 Quefa 的 Plus、Pro 5x、Pro 20x、Pro 50x 四项 CDK 套餐映射到上游 GPT 套餐。
- 只读查看经过脱敏的 CDK 库存、CDK 兑换订单及历史履约记录，用于人工对账。
- 保存供应 Webhook 验签密钥，供 Quefa 入站回调使用。

明确不包含：虚拟支付工具创建、支付资料查询、敏感支付资料展示、相关余额操作、退款、冻结、解冻、删除等功能。上游文档即使提供这些接口，本系统也没有对应路由、服务方法或开放 API。

## 访问方式

本地启动 API 后访问：

```text
http://127.0.0.1:3200/internal/admin/supply
```

页面本身不加载供应数据；所有数据请求必须携带：

```http
X-Platform-Admin-Token: <PLATFORM_ADMIN_TOKEN>
```

`PLATFORM_ADMIN_TOKEN` 应至少 32 个随机字符；默认 `replace-` 占位令牌会被拒绝。生产环境还必须把管理路由放在独立内部域名或 VPN 后，配置 WAF/IP 白名单、人员登录、MFA、RBAC 和审计；当前令牌页是开发/预生产管理入口，不应直接暴露到公网。

内部接口契约见 `openapi/internal-admin.yaml`。代理商接口仍以 `openapi/openapi.yaml` 为准，两者不得合并发布。

## 配置字段

| 字段 | 用途 | 安全规则 |
|---|---|---|
| 内部名称 | 便于运营识别供应连接 | 不对外展示 |
| 环境 | `sandbox` 或 `production` | 切生产前必须重新测试 |
| OpenAPI 基础地址 | 余额、GPT 套餐与对账接口 | 仅 HTTPS，主机名必须在允许名单 |
| CDK 基础地址 | CDK 签发、兑换与对账接口 | 仅 HTTPS，主机名必须在允许名单 |
| API Key | 服务端调用供应接口 | 只写、AES-256-GCM 加密，保存后不回显 |
| Webhook Secret | 验证供应回调 | 只写、加密，保存后不回显 |
| 历史直充资源编号 | 仅兼容已存在的旧 direct 订单 | 只写、加密；当前四项套餐不使用 |
| 启用 | 允许 Worker 使用该连接真实履约 | 还受 `FULFILLMENT_PROVIDER` 总开关约束 |

`SUPPLIER_ALLOWED_HOSTS` 是逗号分隔的精确主机名允许列表。后台拒绝 HTTP、非标准端口、URL 用户名/密码、IP 地址和未列入允许名单的主机；基础路径只能分别为 `/openapi/v1`、`/api/v1/cdk`，不能带查询参数或片段。两个地址必须属于同一主机，已知沙箱/生产域名还必须与环境标识相符。供应请求禁止自动跟随 HTTP 重定向。

## 首次配置顺序

1. 保持 `FULFILLMENT_PROVIDER=mock`，先填写供应方沙箱地址和沙箱 API Key。
2. 保存后执行“测试连接”。测试会同时检查鉴权、余额和 GPT 套餐接口。
3. 执行“同步套餐”，确认四项 GPT 套餐的可售标识和价格版本正确；同步结果中的其他套餐不得映射上架。
4. 为四项 Quefa 商品分别选择上游 GPT 套餐。所有映射生产初始默认停用，确认价格后再逐项启用。
5. 用供应方沙箱完成 CDK 签发、公开码交付和 CDK 自动代充链路，核对入站回调、订单状态、失败重提和金额。
6. 只有沙箱验收通过后，才在受控环境把 `FULFILLMENT_PROVIDER` 改为 `zovocard` 并重启 API/Worker。后台“启用”与环境总开关必须同时满足，真实履约才会发生。

配置保存到共享仓储后，API 与 Worker 每次操作都会读取当前配置，不需要把 API Key 写入代理商配置或前端。修改连接不会回显已有密钥；留空表示保持不变，清除操作需要通过内部 API 的显式 `clear_*` 字段执行。

页面明确显示当前是模拟履约还是供应接口履约。保存时携带已读取的 `config_version`，版本不匹配返回 409；连接测试和套餐同步也校验版本，避免较早发起的请求覆盖刚更新的密钥。切换环境会清空原套餐快照、回调密钥和支付资源；存在未完成订单或有效 CDK 时拒绝切换供应地址、环境或 API Key。停用供应连接阻止新供应写请求，但仍允许查询已提交订单。

## 套餐同步与商品映射

同步只请求 `product=gpt`。系统以返回的 `registry[].key` 作为供应套餐名，并使用 `acc_plan_key` 查找对应价格配置。套餐只有同时满足以下条件才可启用映射：

- `registry[].purchasable = true`
- `plans[acc_plan_key].enabled = true`

每个 Quefa 商品映射包含：Quefa 商品编号、履约模式、供应产品、供应套餐、启用状态和版本。当前只允许 Plus、Pro 5x、Pro 20x、Pro 50x 四项内置 CDK 映射；接口边界会拒绝 direct 模式及任意商品编号。创建订单时保存当时的履约快照，因此后续更改映射不会篡改旧订单。

供应接口履约模式下，新订单要求连接启用、目标套餐已同步为可售、平台映射已启用且代理商品已启用；任一层停用都隐藏商品并阻止接单。同步会为尚未启用的内置商品匹配真实上游套餐键，但不会擅自启用。当前仅支持一个主供应连接，不包含多上游路由或自动切换。

## 回调与对账

供应 Webhook 仍由供应方开发者后台配置到 Quefa 的公开回调地址。上游的 Webhook 配置接口依赖网站登录会话，不适合存入自动化服务，因此当前不在管理后台内自动创建。Quefa 接收回调时使用原始请求体做 HMAC 校验，并按稳定事件 ID 持久化去重。

只读对账响应会主动丢弃上游返回的敏感支付资源字段、原始 CDK 和其前缀，只保留供应订单引用、Quefa 请求引用、产品、套餐、状态、阶段、脱敏账号、金额和时间。该数据仍是平台内部数据，不得返回代理商。

对账邮箱由 Quefa 再次脱敏；管理 API 响应禁止缓存。请求日志不记录 URL 查询参数，也不记录可能带原始输入的异常文本。

## 数据存储

生产目标迁移为 `migrations/0004_supplier_management.sql`：

- `platform_supplier_connections`：平台级供应连接与加密秘密。
- `supplier_plan_snapshots`：充值套餐同步快照。
- `supplier_product_mappings`：Quefa 商品到供应套餐的映射。

三张表都没有 `merchant_id`，因为它们是 Quefa 平台资源，不属于任何代理商；同时全部撤销 `PUBLIC` 权限，代理商数据库角色不得获得访问权。生产环境需要由平台后台专用数据库角色访问，并通过 KMS/Secret Manager 管理数据加密密钥。

## 上线前必须补齐

- 使用真实供应沙箱凭证完成网络联调，并确认固定出口 IP 已加入上游白名单。
- 把 SQLite 沙箱仓储替换为 PostgreSQL 生产仓储并验证迁移、权限和备份恢复。
- 将平台管理令牌替换为人员登录、MFA、细粒度 RBAC 和双人复核；令牌仅作为过渡入口。
- 配置供应回调地址和密钥，验证重复、乱序、签名失败与补偿查询。
- 建立余额阈值告警、套餐变更告警、成本差异工单和每日对账。
- 对管理域名执行网络隔离、日志脱敏、密钥轮换、渗透测试和访问审计。
