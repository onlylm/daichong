# 回调与资金凭证精确查询

日期：2026-10-01（北京时间）  
状态：本地重构分支已完成并通过自动化测试，尚未部署生产。

## 本轮目标

高频回调和资金操作原先有多处“读取整类记录后再 `find/some`”的实现。记录量增加后，一次登录、充值到账通知或上游进度回调可能触发大量 JSON 解码；资金流水防重虽然必须保留，但不能依赖全量内存扫描。

## 已完成

### 上游充值回调

- SQLite 按 `upstreamClientRequestId` 精确读取一笔履约任务。
- 新增对应表达式索引。
- Webhook 的签名、事件防重、状态转换和公开失败信息规则未改变。

### 账号与启动

- 登录按规范化用户名精确查找账号。
- 管理员初始化和账号创建的存在性检查使用有界查询。
- 启动时判断是否需要兼容旧支付宝订单，直接查询一笔旧支付尝试，不再遍历全部历史订单。

### 资金、开票与成本

- 钱包支付宝充值请求号、已入账渠道流水和提现付款流水使用精确条件查询。
- 开票申请号、订单关联和支付宝补差价流水使用精确条件查询。
- 每日核算单付款流水与提现流水交叉防重使用精确条件查询。
- 成本清算凭证、上游交易候选和补差付款请求号使用精确条件查询。

新增用户名、请求号、上游请求号、支付流水、到账流水、付款流水和成本凭证等表达式索引。资金防重仍检查全局唯一范围，只是由数据库定位；没有截断为“最近若干条”，也没有降低重复流水拦截标准。

## 查询能力

通用记录查询增加：

- `ne`：排除当前记录，用于更新或幂等重放时检查“是否被其他记录占用”；
- `not_null`：只选择已有事实值的记录。

内存仓储继续作为测试回退；生产 SQLite 在 SQL 中执行条件、排序和 `LIMIT`。

## 自动化验证

- SQLite 上游请求号读取只执行一条精确查询。
- `ne` 与 `not_null` 组合能正确命中目标资金记录。
- 现有登录、开票、钱包、每日核算、成本核算和充值可靠性用例继续通过。

最终结果以 `npm run check` 为准。本轮不部署生产，也不调用真实支付或充值接口。
