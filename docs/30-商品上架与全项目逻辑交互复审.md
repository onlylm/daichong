# Tibo 商品上架与全项目逻辑交互复审

日期：2026 年 9 月 30 日。对象：平台所有者及后续开发者。

结论：商品卡片确实存在问题，但不能仅通过缩小卡片、增加弹窗解决。当前主要矛盾是商品配置有多个来源，初始化会覆盖部分经营设置，页面没有清楚区分“管理员决定上架”和“供应链实际可售”，采购的异步结果又与前端超时、重试机制不一致。应先修正交易与状态逻辑，再分别设计管理员管理界面和代理商采购界面。

本文是只读复审及待实施方案，不是修复完成说明。未修改业务代码、商品配置、钱包余额或生产部署；未创建订单、发起真实支付退款或运行本地测试。本文补充 [平台成熟化审计][prior]，不替代其中的财务、售后和任务状态分析。

- 最新商品只读快照：北京时间 2026 年 9 月 30 日 09:19。数据库为生产 SQLite，通过只读连接和只读查询取业务字段，没有导出密钥、Session 或初始密码。
- 本轮抽查 catalog-service、global-product-catalog、supplier-management-service、gpt-products、agents、workspace-page 六个源码文件，本地与服务器 current 目录 SHA256 一致。这不等于对整个源码、构建产物逐文件比对。

- 浏览器连接获取页面失败并超时，未完成线上 DOM、桌面/手机、键盘和屏幕阅读器实测。交互结论来自实际源码；涉及焦点、视觉密度和性能的结果均需实机验收。

- UI 复审采用 impeccable 的交互完整性、性能、可访问性、主题和响应式检查维度；文本规则扫描未命中不代表业务逻辑或界面已经合格。

P1 表示可能影响订单、资金、售后判断或核心经营能力，应优先处理；P2 表示交互、可维护性或扩展稳定性问题。本次没有认定正在发生的 P0 事故。

## 不能在改造中改变的业务规则

1. 只有一名平台管理员，不增加第二审批人；资金操作仍需原因、确认、唯一操作号、审计记录和可追溯冲正。
2. 代理不能主动取消已派发充值。只有上游明确失败并确认该次尝试结束，才允许在原订单权益有效时重新提交。超时、断网、处理中、结果未知不等于失败。
3. 代理可选 CDK 或自动直充，自动直充底层用 CDK。失败后提供代理商自己的充值入口或链接，不默认向客户暴露 CDK。
4. 代理自行开发品牌前端，平台提供准确的状态、操作能力和稳定文档。
5. 平台承担的补差退款不冲减代理佣金。商品下架不能抹掉已付款订单的履约权益。
6. 新商品默认草稿或下架，管理员明确发布后才销售。只管理 GPT 相关产品，Codex 点数 CDK 不应因为白名单遗漏而悄悄消失。

## 卡片式商品该如何调整

### 管理员需要管理表而不是采购卡片

当前管理员和代理共用 `buildProductCard`。管理员虽然已不显示代理的购买按钮，但仍沿用采购展示结构；缺少上游映射、具体不可售原因、同步时间、发布变更和影响范围等管理信息。[卡片实现][ui-card]

建议管理员商品页使用紧凑表格：商品及 SKU、提货价、发布状态、实际可售状态、阻塞原因、上游映射、更新时间、操作。状态必须同时显示，例如“已上架 / 不可售：映射关闭”，并提供“查看原因 / 去配置”入口。不要只给一个“配置”按钮让管理员逐页寻找。

短编辑使用弹窗；映射、价格历史、发布检查使用详情抽屉；订单、工单等需要稳定链接和完整历史的内容保留独立详情页。不是所有页面都塞进弹窗。

### 代理商可以保留卡片但需收敛操作

| 设计问题 | 当前影响 | 建议 |
| --- | --- | --- |
| 卡片“生成 CDK”和“创建订单”，底部又有“生成 CDK” | 同一采购有多个入口，不容易分清交付方式和付款方式 | 一个主入口“购买 / 充值”，进入后选 CDK 或自动直充 |
| 商品名含“CDK 兑换”，同时标注支持自动直充 | 把底层供应方式和客户交付方式混在一起 | 标题用套餐名称；交付方式独立显示 |
| “启用中”“已停用”混用管理状态与实际可售 | 不清楚平台停售还是暂时供应受阻 | 代理显示可购买、暂不可售及友好原因；不暴露密钥或内部故障栈 |
| 金额突出但币种和用途依赖上下文 | 可能混淆人民币提货价、上游 U 服务费和客户售价 | 明确“采购价 CNY”“本次扣采购余额”，不同币种不相加 |
| 快速选择器的名称缩写不完整 | Go 和 Pro 20x 续费启用后都可能缩写成 ChatGPT | 保留套餐、倍率、续费属性和周期，不按第一个单词截断 |

## 商品发布逻辑发现

### G01 启动代码会关闭手动启用的 Go 映射

**P1，代码确定，线上状态与问题条件一致。** Go 的内置模板价格仍为零；启动的 supplier seed 用模板价格判断商品是否有效，而不是读取管理员保存的全局 38 元价格。只要 Go 映射开启，下次执行初始化就会被关闭。API 和 Worker 初始化均经过该逻辑。

修复方向：默认模板只负责首次创建，后续不能用模板价格覆盖经营状态。初始化迁移应版本化、只执行一次。验收：Go 定价并发布后，重启 API 和 Worker，其映射、价格、发布状态均不变。本轮未实际重启复现。

依据：[Go 模板][gpt]、[seed 映射逻辑][supplier-seed]、[启动顺序][boot]。

### G02 自定义商品名可能在重启后被恢复

**P1，代码风险。** `reconcileProductGrants` 把租户商品名称与内置名称比较，不同就恢复模板名称，并增加租户价格版本。全局目录仍可能保留自定义名称，管理员看到的名称与代理看到的名称会分裂。

修复方向：经营名称只从全局商品版本或明确租户覆盖项读取；启动不改名。验收包含改名、重启、管理员与代理一致、历史订单名称快照不被篡改。[租户商品重整][grant-seed]

### G03 默认禁售被初始化规则破坏

**P1，代码确定。** 全局目录初建时，只要模板价格大于零就自动上架；另一个启动函数又把价格版本为 1、价格大于零的禁用商品授权改成启用。这不符合新商品默认关闭的要求。

不是所有手动下架都会被恢复：该函数有版本为 1 的条件，不能扩大为“每次启动都会上架所有商品”。应移除持续运行的默认开售规则，新增商品以草稿或下架入库，迁移不得推断管理员授权。[全局初始化][global-seed] [默认激活][agent-seed]

### G04 Codex 点数在同步与商品管理之间被排除

**P1，线上数据与代码共同确认。** 上游套餐已同步，但 `managedGptProducts` 仅包含五个订阅商品。商品列表、映射列表、映射保存都受这份白名单控制，初始化还会关闭白名单外的旧映射及授权。

恢复点数不能只点击“同步套餐”。需要补齐六档点数的商品定义、映射、销售价格、交付支持及文档，并默认下架，逐个发布。历史直充产品记录保留供查询，不进行破坏性删除。[商品定义][gpt] [目录过滤][catalog] [映射限制][mapping]

### G05 全局目录并非真正的统一配置来源

**P1，结构风险，当前活跃代理抽查未见错价。** 全局保存把名称、价格、可售位复制到 active 商户授权；查询和下单读取租户授权。旧的单代理商品修改路由仍存在，暂停商户不参与全局更新，租户价格版本又会被赋值为全局商品版本。

后果包括单代理与全局配置漂移、暂停商户恢复时沿用旧值、版本不再单调，以及“已同步全部代理商”的提示与实际更新范围不符。

修复方向：建立唯一全局商品版本；租户只保存授权和明确允许的覆盖字段。如果业务采用统一价，就关闭旧的单代理改价入口。确需投影时，要有版本追踪与补偿，而不是用多个可写副本表示同一配置。[全局保存][global-save] [租户读取][catalog] [旧商品接口][legacy-product]

### G06 上架成功不等于可售且原因不够具体

**P1，线上确有五个上架但只有三个可售。** 保存上架仅校验商品、价格和版本；真实可售还受映射、连接、缓存套餐是否可售等限制。返回的原因却主要是“销售通道尚未启用”，不能区分问题所在。

建议把发布状态与供应就绪状态分开，保存配置和发布操作分开。发布前展示检查结果；商品发布后供应异常则标为“已上架但受阻”，不偷偷改成管理员主动下架。检查项包括价格、映射、连接、套餐支持及快照时效；付款方式和余额另外在结算时校验。[可售计算][catalog] [全局状态输出][global-list]

### G07 映射保存缺少语义核对和版本冲突保护

**P1，误配置风险。** 保存映射会检查所选套餐存在且可售，但不会核对 Plus 是否误选 Go 或点数包；输入也没有期望版本。一个管理员开两个旧标签页仍可能覆盖新配置。

建议按订阅或点数、倍率、周期和续费属性分组候选项；保存前显示旧值、新值及影响，只允许明确确认的特殊映射。加入乐观版本校验，不能自动猜测后直接启用。[映射保存][mapping]

### G08 下架与改名也被价格校验阻止

**P2，边界问题。** 保存接口一律要求价格大于零，表单同样必填。对尚未定价的草稿，只想保持下架或改名也必须先设置正价格。

草稿和下架允许未定价；发布时才要求有效正价格。下架确认应说明“停止新订单，不影响已付款权益”。[全局保存][global-save] [编辑弹窗][ui-pricing]

## 交易和接入风险发现

### T01 生成 CDK 的超时重试可能创建重复采购

**P1，优先于卡片美化。** 前端请求 15 秒超时，生成 CDK 的后端却会等待签发，循环窗口为 30 秒，单次上游等待还可能使实际耗时更长。前端没有传稳定的 `merchantOrderNo`，后端缺省值来自每次请求 ID。超时时订单可能已创建并扣款，用户再点就可能新建一单、再扣一次。

普通采购弹窗也在每次提交时生成新订单键。快速栏调用生成函数未返回其 Promise，按钮的加载锁还可能提前释放。后端已有订单幂等能力，但界面未正确复用。

修复方向：一次采购意图使用固定键；创建后立即返回订单 ID，签发交给 Worker，页面轮询同一订单。超时显示“正在核对创建结果，请勿重复提交”，不能直接建议重新购买。当前 HTTP 发码循环还会领取全局可签发订单，应从请求路径移出。

验收：模拟响应超时、双击、多入口点击和响应丢失，均只能产生一个采购订单和一次扣款，重连后能查回原结果。[前端请求与生成][ui-api] [生成路由][cdk-route] [同步等待][cdk-wait] [快捷栏][ui-dock]

### T02 供应配置暂停可能使已付款 CDK 进入不可自动恢复的失败

**P1，代码风险；当前快照未见 failed CDK 样本。** 供应连接关闭或缺少凭证会产生不可重试的配置错误，签发将 CDK 标成 failed；签发领取只处理未创建的券或 issuing 券，恢复配置后不会自动领取 failed 券。

“暂时暂停执行”不等于“上游明确拒绝发码”。需要区分配置待修复、结果未知、上游明确失败；配置恢复后在原订单与原上游幂等键下继续核对或执行，提供管理员恢复任务入口，不让代理再买一单解决。[连接检查][supplier-client] [签发状态与领取][cdk-service]

### T03 API 开通状态与实际鉴权规则不一致

**P1，代码风险。** 等级升级可写入 enabled 并使用 tier 前缀表示开通来源；鉴权只直接认可 manual 来源，否则要求找到对应已入账充值记录。由等级自动授予的权限可能界面显示已开通、可生成密钥，实际调用却被拒绝。生产读取到的 tier 来源记录当前未启用，不能宣称已有启用账号正在因此报错。

另一个问题是充值开通资格先取第一笔已核实充值，再检查是否达到 110 元，而不是查找符合门槛的记录。多笔不同金额充值时，判定可能依赖返回顺序。

应建统一授权服务，明确人工、等级、充值三种来源；资金资格根据明确的单笔或累计规则计算，鉴权与后台展示必须使用同一结果。[等级授权][tier-api] [鉴权][auth] [充值资格][api-deposit]

### T04 等级权益展示与采购报价不一致

**P1，经营承诺不一致。** 等级规则和权益文案仍包含不同会员采购价，但当前报价路径采用统一商品价格，`tierEffectiveSupplyPrice` 直接返回基础价。

应先统一产品决策：若全网统一提货价，移除不再兑现的会员优惠说明；若保留等级价，报价、订单快照、余额扣款和文档统一使用一套规则。本报告不擅自恢复旧优惠，也不认定已发生历史多扣。[权益与报价规则][tier-prices]

### T05 notify_url 与实际事件投递语义不一致

**P1，接入契约风险。** 创建订单检查 notify_url 已登记，但没有将它作为订单专属投递目标保存；事件按商户全部匹配订阅的启用回调地址投递。一个代理运营多个站点时，不能认为传入某个地址就只发往该站点。

这是同租户的投递范围问题，不是本轮发现了跨租户泄露。应明确选择“租户广播”还是“应用或订单级路由”，实现与文档一致，并给代理重复事件、乱序事件的处理示例。[订单参数处理][api-order] [事件广播与地址检查][webhook]

### T06 Webhook 出站地址安全边界不足

**P1，代码风险，未做攻击或内网探测。** 地址校验主要限制协议，未见私网、回环、链路本地地址及 DNS 解析结果的拦截；投递 fetch 未显式限制跳转。因此存在让服务端访问非预期目标的风险，实际可达性未验证。

应校验公网目标及解析结果、限制或逐跳校验重定向，结合运行环境出站策略，并对响应大小和超时设限。不能只用字符串里是否包含域名来防护。[地址校验][api-url] [投递请求][outbox]

### T07 支付过期和关闭结果缺少完整业务投影

**P2，生命周期缺口。** 支付宝普通订单和钱包充值的核对主要推进成功，未见将明确关闭、长期未创建交易及本地过期整理为完整终态的对应路径。页面可判断过期，但记录仍可能 pending 或 requested，并持续查询。

应区分“本地付款入口过期”“渠道明确关闭”和“支付结果待核对”；保留迟到付款的查询与异常处理，不可单凭本地计时就推断没有付款，更不能因此开放重复充值。[钱包支付宝核对][wallet-alipay] [订单支付宝核对][alipay]

### T08 多实例防重放能力尚未接入共享存储

**P2，扩容前置项。** 运行时仍使用 MemoryNonceStore。重启或扩成多个实例后，已使用 nonce 不是共同可见。后端业务幂等仍可减少重复交易影响，因此不能夸大为所有请求必然重复扣款。

启用共享且原子写入的 nonce 存储，保证过期窗口和实例间一致性，再考虑扩容。[鉴权实例初始化][nonce]

## 全局交互发现

### U01 失败订单筛选只筛当前页

**P1，影响售后判断。** 后端先按搜索和商品分页，状态没有进入请求参数；前端仅对当前页结果过滤。第一页没有失败单而后面有时，会显示“暂无符合条件的订单”，甚至因为空列表分支不渲染分页而无法继续查找。汇总总数也不是状态筛选后的总数。

必须把支付状态与履约状态筛选移到后端，在分页前完成；列表、总数、统计和导出使用同一条件。验收至少构造两页数据，目标状态仅在第二页。[前端筛选][ui-orders] [后端分页][order-list]

### U02 取消确认会被通用表单当成正常完成

**P2，造成表单内容丢失。** inlineForm 只要回调没有抛错就执行 onSuccess 关闭弹窗；商品启停确认取消、采购余额不足或扣款确认取消时，业务回调直接 return，也会关闭原表单。

应明确返回 completed、cancelled、blocked 等结果，只有真正完成才关闭；未执行或校验失败保留输入。涉及已创建订单的情况则转入原订单状态视图，不能把“关闭弹窗”作为完成标准。[表单容器][ui-form] [商品确认][ui-pricing] [采购回调][ui-checkout]

### U03 搜索和轮询采用整页重建加双层缓存

**P2，代码可解释卡顿感，但未测实际延迟。** 商品输入防抖触发 render，替换视图节点，有丢焦点和光标位置的风险；change、回车和防抖又各自触发。30 秒请求缓存、60 秒页面缓存与 3 秒订单轮询冲突，部分刷新可能仍显示旧状态。

搜索只更新结果区，保留输入节点；活动订单使用无旧缓存的状态查询并更新对应行；取消过期请求，离开页面或关闭弹窗时结束轮询。前端超时不等于业务失败。[搜索][ui-search] [请求缓存][ui-api] [前次性能分析][prior]

### U04 页面汇总口径和状态命名不够明确

**P2。** 概览存在按最近 50 条订单计算的成功或待处理统计，而总订单数来自全量。商品“已停用”筛选又包含所有实际不可售商品，包括配置仍上架但映射关闭的商品。

全量指标应由后端聚合，近期样本明确标注范围；上架、供应、支付、CDK 签发、充值履约分别保留状态，不用一个“失败”或“启用”统包。不能让用户从通用错误词猜下一步。[概览与商品统计][ui-overview] [状态筛选][ui-status]

### U05 视觉与可访问性应在逻辑修复后实测

**P2，代码预审，不是可访问性认证。** 页面已有原生 button、label、dialog、焦点样式和移动端布局，这是可复用基础。仍有 10 至 11 像素辅助文字、小触控按钮、旧新 CSS 重复覆盖；减弱动效规则主要压缩 transition，未统一处理 animation。

建议统一主题 token 和组件状态，清理覆盖链；提高关键状态文字可读性，按移动端操作便利性扩大点击区域；补测弹窗焦点归还、长表单键盘使用、200% 缩放、窄屏横向溢出、错误通知读屏、对比度及减少动态效果。未实测前不声称某项 WCAG 已达标，也不把 34 像素按钮直接等同于确定违规。[样式与响应式][ui-style]

## 与前次审计合并的整改清单

下列仍是本项目整体整改范围，详细实现证据和建议见 [前次报告][prior]。本轮没有通过部署修复它们，也不重复认定新的生产事故。

| 模块 | 应优先闭环的问题 | 目标 |
| --- | --- | --- |
| 履约任务 | 本地取消运行任务可能放行重提 | 上游明确失败后才结束尝试，原订单可重提，未知继续核对 |
| 财务佣金 | 普通部分退款和补差退满的佣金回冲口径 | 统一计算与记账规则，补差由平台承担 |
| 钱包 | GET 查询触发佣金记账，人工调账能力不足 | 事件记账、查询只读；管理员单人增加或减少余额并完整留痕 |
| 退款 | 渠道结果未知缺少恢复任务 | 复用退款号查询，未知保留额度，不盲目重复退款 |
| 工单和邮件 | 异常、工单、任务、通知未形成闭环 | 同一异常聚合为 case，明确负责人、下一步、升级时限与通知 |
| 后台任务 | 多种工作串行、Webhook 租约与批量耗时不匹配 | 队列隔离、可恢复租约、重试和告警，不靠页面刷新推进 |
| 开发文档 | 状态枚举、事件、版本和旧财务描述不一致 | 文档由运行契约约束，示例覆盖异常、幂等、重提及品牌入口 |
| 运维 | 健康检查、存储实际使用与部署认识不一致 | 验证实际数据源、正确探针、备份恢复演练及版本可追踪 |

通知是状态变更后的告知，不是状态判断依据。邮件只携带安全摘要和授权详情链接，不放 Session、密钥或可直接盗用的兑换凭证。收件人按代理订单归属与平台异常类型选择；同一事件去重，未知结果定时升级，不每次轮询发一封。

## 推荐结构与实施顺序

商品链路应明确为：供应套餐快照 → 平台商品草稿及映射 → 发布检查和商品版本 → 代理授权与报价 → 订单不可变快照 → CDK 签发与充值尝试。同步上游只更新快照，不能自动上架；启动只执行明确版本迁移，不能替管理员重新配置。

发布状态、供应可售状态和用户付款能力分别表达。改价格或下架只影响后续新交易；已经形成订单的金额、套餐、供应映射应按订单快照执行。管理员能查看影响范围和版本，代理只看到适合购买决策的信息。

1. **先防重复交易与错误终态。** 修复 T01、T02 及前次任务取消、退款未知结果、佣金口径；统一业务幂等与异常分类。
2. **修商品全链路。** 处理 G01 至 G08，恢复需要的点数 CDK 草稿，去掉启动覆盖，建立状态诊断和明确发布动作。
3. **对齐权限与接入契约。** 处理 T03 至 T06，统一 API 授权、会员权益、回调范围及安全边界；同步修正文档。
4. **重整管理员与代理界面。** 管理表格与采购卡片分开，修筛选、弹窗结果、查询缓存，再完善工单待办、邮件和深链接。
5. **完成生命周期及运行保障。** 支付过期与迟到款、共享 nonce、队列隔离、性能量测、恢复演练和发布检查。

适合复用现有代码，而非整体推翻：已有租户隔离、签名与 CSRF 校验、订单快照、上游发码幂等键、支付配置版本、敏感充值凭据加密、任务租约、Webhook 重试和审计记录。支付宝路径已有官方 SDK 调用及交易绑定校验，不应因早期截图就认定当前仍是自编收款。

单纯商品下架目前不会要求旧订单重新读取新价格或新映射，这是正确方向；要保留。供应连接全局关闭造成的执行失败则需单独修复，不能将两种开关混成一个。

## 实施后的验收条件

以下是待执行用例，不是本轮测试结果。交易异常用隔离环境、供应模拟器或明确批准的服务器测试环境验证，不能直接在生产制造重复付款。

- Go 定价并发布后重启 API、Worker，名称、价格、映射和状态均不变。
- 新增商品及新增上游套餐默认下架；同步、启动不自动开售。
- 六档点数可作为独立草稿配置，映射错误有明确提示，未发布不能下单。
- 商品发布检查给出具体阻塞项；管理员和代理显示一致但不同权限粒度的信息。
- 已付款订单不受之后改价或下架影响；停止新售与暂停执行可分别控制。
- 同一个管理员两个标签页改配置有版本冲突保护；暂停代理恢复后的目录与现行规则一致。
- 快捷采购、普通采购、超时重试和响应丢失只生成一个订单、扣款一次，并能查回原结果。
- 配置修复后的发码任务恢复原意图，不另下新单；结果未知先查询，不直接判失败。
- 上游排队、运行、超时均不能由代理取消重提；明确失败后才开放原订单下一次尝试。
- 第二页才存在的失败订单可以正确筛出，分页、汇总和导出一致。
- 确认取消、余额不足、校验失败时保留表单输入；提交中禁止重复操作。
- 活动订单状态更新绕过旧缓存，关闭弹窗后不继续后台轮询。
- CDK 与自动直充交付准确；直充失败返回可用的代理充值入口，不泄露底层 CDK。
- 人工、等级、充值开通的 API 权限，界面、密钥签发和真实鉴权一致。
- 多笔充值不因查询顺序改变开通资格，会员权益与实际扣款规则一致。
- 同一代理多个网站的 Webhook 投递范围符合契约；重复和乱序事件可以安全处理。
- 回调目标及跳转不能触达受限地址，共享 nonce 在多实例下保持一致。
- 普通部分退款、平台补差、补差退满的佣金和钱包流水符合既定规则。
- 管理员增减余额通过专用账本操作完成，不直接改聚合余额；可查看前后值、原因及关联单。
- 付款过期、明确关闭、迟到成功和渠道查询未知分别有明确状态及下一步。
- 邮件、工单和待办指向同一异常，已解决事件不持续告警，通知不包含敏感凭据。
- 桌面、窄屏、键盘、200% 缩放和弱网场景完成实测后再认定 UI 合格。
- 记录真实的首屏时间、交互延迟、接口 P95、队列延迟；本轮未给出性能达标结论。
