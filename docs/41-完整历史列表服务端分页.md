# 完整历史列表服务端分页

状态：已在本地重构分支实现并通过自动化测试，尚未部署生产。

## 改造范围

后台原有工单、开票申请和每日核算单页面会一次读取全部历史记录，代理详情中的售后、开票和核算记录也会先取全量后再筛选。数据增长后，接口 JSON 解码、网络传输和表格 DOM 都会随历史总量增长。

本轮完成以下调整：

- `GET /workspace/api/tickets` 支持 `merchantId/status/page/limit`，归档工单在数据库层排除。
- `GET /workspace/api/invoices` 支持 `merchantId/status/page/limit`。
- `GET /workspace/api/daily-settlements` 支持 `merchantId/status/page/limit`。
- 平台总列表每页 20 条；代理详情中的售后、开票每页 15 条，核算单每页 10 条。
- 平台工单、开票和核算页面增加状态筛选，筛选后回到第一页。
- 代理详情不再读取全平台工单后在浏览器筛选，而是直接请求当前代理范围。
- 增加 `(kind, merchant_id, status, updatedAt, id)` SQLite 组合索引，匹配按代理、状态、更新时间分页的常用路径。
- 分页控件提供总数、页码、上一页和下一页；使用导航语义和状态播报，窄屏下自动换行。

## 权限与数据边界

平台账号可以按代理商筛选。代理账号即使伪造 `merchantId`，服务层仍执行租户范围校验；正常请求固定使用自己的代理范围。分页只改变读取方式，不改变工单、开票、核算单的写入、审核或资金规则。

首页行动中心仍只读取最近 8 条待办并返回全量计数，不复用完整历史页；两者用途不同，避免为了显示首页摘要再次读取整页历史。

## 前端统计口径

开票页的“全部申请”使用服务端分页元数据中的全量总数。待办、补差金额和已开票数量标记为“本页”，避免把当前 20 条的统计误认为全部历史统计。若后续需要全量金额汇总，应新增数据库聚合接口，不得重新在浏览器读取全部申请求和。

## 自动化验证

SQLite 集成测试创建多页工单、开票申请和每日核算单，验证：

- 状态筛选后的总数、页数和第二页数据量正确；
- 三类查询均实际调用仓储分页方法；
- 代理范围正确下推；
- 已归档工单不进入完整历史列表；
- 工作台内嵌脚本语法检查、TypeScript 类型检查及相关回归测试通过。

本轮没有连接生产数据库、没有修改生产订单或资金，也没有部署服务器。生产发布须等本地重构全部完成后统一备份生产 SQLite，再按最终发布清单同步。
