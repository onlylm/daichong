# 开放平台历史接口游标分页

## 修复内容

开放平台原有文档把订单、财务台账和结算单声明为游标分页接口，但旧实现存在以下问题：

- 订单先读取当前代理全部订单，再在内存筛选和分页，并逐笔读取最新履约；
- 台账忽略 `from`、`to` 和 `cursor`，直接返回全部记录；
- 结算单忽略 `cursor`，直接返回全部记录。

本次把三类查询下推到 SQLite：

- `GET /v1/orders` 按代理、付款状态、创建时间和游标读取，并在同一数据库查询中关联每笔订单的最新履约；
- `GET /v1/ledger` 支持 `from`（含）、`to`（不含）、`cursor` 和 `limit`；
- `GET /v1/settlements` 支持 `cursor` 和 `limit`；
- 三类接口每页最多 100 条，台账和结算单默认 50 条，订单仍默认 20 条；
- 游标必须属于当前代理且满足当前筛选条件，否则返回 `invalid_cursor`，防止跨租户或跨筛选误翻页；
- 返回顺序使用业务时间倒序、记录编号倒序，新增历史不会造成整表读取。

## 兼容性

响应结构保持 `data + next_cursor`。`next_cursor=null` 表示没有下一页。代理商应完整跟随 `next_cursor` 翻页，不应假设一次请求返回全部台账或结算单。

内存仓储仅用于测试，继续保留内存分页回退；生产 SQLite 走索引化游标查询。新增订单付款状态/创建时间和台账发生时间组合索引。

## 验证

集成测试通过真实签名请求验证：

- 多页订单无重复，付款状态在分页前筛选；
- 台账日期范围和多页游标生效；
- 结算单多页游标生效；
- 不存在或不属于筛选范围的游标被拒绝；
- SQLite 路径未调用订单、台账或结算单全量列表方法。

本地分支尚未部署生产。最终发布前还需在生产数据库只读副本上验证游标查询计划与响应耗时。
