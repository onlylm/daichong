# Quefa 多代理商分销开放平台架构与实施方案

版本：v0.1（2026-09-25）  
读者：产品、研发、运维、安全、财务、客服与管理层。

## 1. 目标与边界

新平台把当前单平台方模式扩展为多个代理商/销售渠道。消费者始终在代理商自有商城下单，代理商只负责推广、销售页面和调用 Quefa 开放接口；Quefa 使用自己的支付宝统一生成二维码、收款、查付和原路退款，并负责 Session 履约、失败原因、Webhook、对账和差价结算。代理商不提供支付宝账号或密钥。

硬边界：新域名、新服务器、新 PostgreSQL、新 Redis、新 KMS/主密钥，以及由 Quefa 管理的新系统专用支付/上游配置；不得共享原生产数据库或直接迁移密钥。支付配置是 Quefa 平台级资源，绝不按代理商配置。首期采用模块化单体，API 与 Worker 独立进程，不提前拆微服务。

业务角色与资金流以 [《业务角色与资金流》](./00-业务角色与资金流.md) 为准。数据库中的 `merchant_id` 是租户技术名称，业务上指代理商/销售渠道，不代表支付宝收款商户。

## 2. 总体架构

```text
代理商商城 ──HMAC──> API 进程 ─────> PostgreSQL
                         │                 │
                         ├── Nonce/限流 ─> Redis
                         │                 │ Outbox/任务
Quefa支付宝异步通知 ───> │                 ▼
                         └────────────> Worker 进程
                                           ├─ 支付查询/退款
                                           ├─ 上游履约
                                           ├─ Webhook 投递
                                           └─ 对账/结算任务

代理商后台 ─账号/RBAC─> 管理端 API（同一代码库、独立路由域）
平台运营 ──MFA/RBAC───> 内部管理端 API
```

API 只做鉴权、校验、短事务和任务入队。Worker 通过 `FOR UPDATE SKIP LOCKED` 领取任务，所有外部副作用均持久化意图后执行。Redis 丢失不破坏订单和财务事实，PostgreSQL 是唯一业务事实源。

## 3. 模块边界

| 模块 | 职责 | 不得承担 |
|---|---|---|
| Identity | 代理商账号、平台账号、RBAC、MFA、会话 | API HMAC 密钥明文展示 |
| Partner App | 应用、密钥轮换、IP 白名单、Nonce、签名 | 订单业务逻辑 |
| Catalog | 商品主数据、代理商授权、供货价、销售上限 | 上游真实成本对外暴露 |
| Order | 幂等开单、订单查询、时间轴 | 直接确认到账 |
| Payment | Quefa 平台级支付抽象、预创建、通知验签、主动查单 | 按代理商配置支付账户；以同步跳转确认支付 |
| Fulfillment | Session 加密、任务、状态映射、失败原因 | 在结果未知时重复提交 |
| Refund | 普通退款、补差退款、审核和支付通道执行 | 请求内无审计直接出款 |
| Ledger | 不可变双向分录、余额投影、对账差异 | 修改历史分录 |
| Settlement | 周期结算、封存、付款登记、后续冲正 | 回写已封存结算单 |
| Webhook | 订阅、事件、投递 Outbox、签名、重试 | 同步阻塞业务事务 |
| Audit | 操作人、主体、前后值、请求关联、理由 | 保存 Session/secret 明文 |

## 4. 多租户隔离

每个代理商拥有独立 `merchant_id`、账号、应用、API 密钥、IP 白名单、商品授权、价格、订单、Webhook、退款、台账和结算单。所有代理商共享 Quefa 的集中支付能力，但业务数据严格隔离；任何代理商均不能读取或配置支付宝凭证。

隔离采用四层防护：

1. 身份层：签名先定位 `partner_id + key_id`，只生成一个不可变租户上下文。
2. 应用层：仓储方法禁止可选租户参数，必须显式传入 `merchant_id`；按 ID 查询仍追加租户条件，未命中统一返回 404。
3. 数据库层：所有租户表包含 `merchant_id`，唯一键均包含租户维度；事务开始执行 `SET LOCAL app.merchant_id`，PostgreSQL RLS 使用 `current_setting('app.merchant_id')`。
4. 测试与审计：跨租户 IDOR、幂等键碰撞、Webhook/结算读取均有自动化测试；每次访问记录 `request_id/merchant_id/app_id/key_id`。

内部财务查看上游真实成本需要 `platform_finance_cost` 权限，代理商角色永不获得该字段。平台超级管理员也不得绕过审计；紧急越权采用限时 Break Glass 并告警。

## 5. API 安全协议

请求头：`X-Partner-Id`、`X-Key-Id`、`X-Timestamp`、`X-Nonce`、`X-Signature`；变更类请求还须 `Idempotency-Key`。签名串：

```text
METHOD\n
PATH\n
CANONICAL_QUERY\n
TIMESTAMP\n
NONCE\n
KEY_ID\n
IDEMPOTENCY_KEY\n
LOWERCASE_HEX_SHA256(RAW_BODY)
```

签名为 `lowercase_hex(HMAC-SHA256(client_secret, canonical_string))`。服务端允许时钟偏差 ±300 秒；Nonce 在同一 `partner_id/key_id` 下 10 分钟唯一；签名通过后才写 Nonce。原始请求体字节参与摘要，JSON 不在服务端重新序列化。密钥只在创建/轮换时显示一次，库中保存 `HMAC-SHA256(pepper, secret)` 的验证材料或经 KMS 包封的 secret；日志永不记录签名、Cookie、Authorization、Session 或请求体中的敏感字段。

密钥轮换为“创建新 key → 双钥并行 → 代理商切换 → 观察 → 吊销旧 key”。吊销即时生效，密钥有 `active/expiring/revoked` 状态和可选有效期。

## 6. 可靠性与一致性

- 订单创建、事件写入、财务分录、任务创建在同一数据库事务中完成。
- Outbox 记录含唯一 `event_key`，Worker 领取后投递；成功写 `delivered_at`，失败指数退避并加抖动，达到上限进入死信待人工重放。
- 外部调用使用稳定业务幂等号：支付预创建=`payment_attempt_id`，上游履约=`fulfillment_id`，退款=`refund_id`。
- 任务租约超时可重新领取，但副作用前后均做幂等查询。结果未知的履约/退款只查状态，不重复提交。
- API 幂等表保存租户、路由、幂等键、请求摘要、响应码和响应体；同键同请求重放原响应，同键异请求返回 `idempotency_conflict`。

## 7. 敏感数据

Session 与上游临时凭证使用 AES-256-GCM，每条记录随机 IV，数据密钥由独立 KMS 主密钥包封并带 `key_version`。密文的 AAD 至少含 `merchant_id/order_id/fulfillment_id`，阻止跨记录搬运。终态成功/失败且不再需要复核后立即清除密文、IV、Tag 和包封数据密钥，仅保留邮箱哈希、脱敏邮箱、清理时间与审计事实。

日志采用字段白名单，Pino 强制脱敏；异常栈不得包含请求体。数据库备份加密，恢复环境使用独立密钥。任何导出均异步生成、短期有效、带水印与审计。

## 8. 状态机原则

- 状态只能通过显式转换表改变，非法转换返回 409 并写审计。
- 支付、履约、退款、补差退款、结算、Webhook 各自独立；禁止用一个“订单状态”覆盖所有事实。
- 每次转换写入 `state_transitions`，包含旧状态、新状态、原因、操作者、关联请求和时间。
- 支付成功并不等于履约成功；履约失败不自动把支付改为退款；退款成功通过独立事件影响财务余额。

## 9. 财务模型

金额一律使用 PostgreSQL `bigint` 分表示，币种 ISO 4217；禁止浮点数。订单价格在开单时快照。

必须区分：用户向 Quefa 支付的金额、Quefa 支付渠道实际收款、Quefa 对代理商供货价、普通退款、补差退款、代理商销售差价、代理商待结算、支付手续费、上游真实成本、Quefa 毛利。

```text
代理商销售差价 = Quefa实际收款 - Quefa供货价 - 约定由代理商承担的普通退款 - 补差退款
代理商待结算净增加 = 代理商销售差价（实际采用分录，可为负调整）
Quefa毛利 = Quefa供货价 - 上游真实成本 - 支付手续费 - Quefa承担的退款成本/其他成本
```

示例：买家向 Quefa 付款 135 元、Quefa 给代理商供货价 110 元，无退款时代理商差价 25 元；Quefa 向买家补差退款 10 元后代理商差价 15 元。若退款发生在结算封存后，旧结算单保持不变，新建下一期 `settlement_adjustment` 负向分录并关联原订单、原结算行和退款。

## 10. 进程与部署

同一镜像通过命令区分：

- `api`：Fastify，健康检查、开放 API、管理端 API、支付回调。
- `worker`：支付确认、履约、Webhook、退款、对账、结算计划。
- `migrate`：单次执行版本化迁移；生产发布前备份，迁移失败即停止。

首期建议单地域：负载均衡/反向代理 + 2 个 API 副本 + 2 个 Worker 副本 + 托管 PostgreSQL 主备 + Redis 高可用。网络默认拒绝，数据库与 Redis 不暴露公网，出口 IP 固定用于上游白名单。

## 11. 可观测性与 SLO

指标：请求成功率/P95、签名失败、Nonce 重放、开单到支付时延、支付通知与主动查询差异、履约队列深度/时长/失败码、退款审核时长、Outbox 延迟/死信、账实差异、结算负余额。日志携带 `request_id/trace_id/merchant_id/order_id`，但不含敏感值。

首期目标：开放 API 月可用性 99.9%；已受理请求不丢失；支付与退款账实差异每日归零或形成可解释工单；RPO ≤ 5 分钟，RTO ≤ 60 分钟（需完成恢复演练后生效）。

## 12. 实施阶段

### 阶段 0：基础与设计（本次交付）

文档、OpenAPI、签名 SDK 示例、PostgreSQL 迁移、API/Worker 骨架、模拟支付/上游、单元测试与跨租户测试。

### 阶段 1：可联调沙箱

接入真实 PostgreSQL/Redis 仓储、后台账号/RBAC、完整 Outbox Worker、沙箱门户、Webhook 重放、财务投影与对账报表；使用全新测试密钥。

### 阶段 2：预生产

Quefa 自有支付宝沙箱/新系统专用应用、上游测试账户、WAF、KMS、监控告警、备份恢复演练、压测、渗透测试、财务 UAT。代理商无需提供支付宝资料。

### 阶段 3：灰度上线

先接一个低风险代理商与小额商品，限制日订单/金额，双人复核退款与结算；观察至少一个完整结算周期后扩容。

## 13. 主要风险与控制

| 风险 | 控制 |
|---|---|
| 跨代理商越权 | 强制租户仓储 + RLS + IDOR 测试 + 404 隐藏资源存在性 |
| 重复扣款/履约/退款 | 三层幂等、稳定外部请求号、未知结果只查询 |
| 账务口径漂移 | 不可变分录、每日支付对账、结算封存、冲正而非改历史 |
| Session 泄漏 | 信封加密、AAD、短期保留、终态清理、日志白名单 |
| Webhook 丢失 | 事务 Outbox、签名、退避、死信、人工重放 |
| 代理商开放 API 密钥泄漏 | 一次显示、双钥轮换、IP 白名单、速率限制、异常告警 |

## 14. 架构验收门槛

- 任意跨租户 API 访问均返回 404/403，测试覆盖订单、退款、账单、结算、Webhook。
- 幂等冲突、Nonce 重放、过期时间戳、错误签名均有测试。
- 财务示例与结算后退款冲正能由分录重放得到一致余额。
- Session 终态清理、日志脱敏、备份加密与恢复演练有证据。
- 代码、配置和文档不存在生产秘密或真实 Session。
