# 历史分页分层并发验证

日期：2026-10-01 13:05（北京时间）  
状态：本地重构分支验证通过，尚未部署生产。

## 验证对象

基准脚本 `scripts/benchmark-history-pagination.mjs` 为同一代理分别生成以下五类历史数据：

- 工单；
- 开票申请；
- 每日核算单；
- 资金流水；
- 操作审计。

每档同时发起 40 个已登录工作台 GET 请求，即每类 8 个请求；请求页大小固定为 20，交替读取前 5 页。脚本验证 HTTP 状态、返回数组上限、总数和查询次数，任何接口返回全量数据、总数错误或多执行分页查询都会直接失败。

运行命令：

```text
npm run bench:pagination
```

## 本次结果

环境为本机 Node.js 单进程、内存 SQLite、Fastify `inject`，不含真实网络和反向代理。

| 每类历史记录 | 并发请求 | 分页查询数 | 整批墙钟 | P50 | P95 | 最大响应体 |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 40 | 40 | 68.04ms | 67.45ms | 67.82ms | 17,251 bytes |
| 1,000 | 40 | 40 | 169.96ms | 169.40ms | 169.80ms | 17,253 bytes |
| 5,000 | 40 | 40 | 390.44ms | 389.98ms | 390.34ms | 17,254 bytes |

结论：在本次受控环境下，5000 条/类别时仍满足方案中“普通列表 API P95 小于 500ms”的本地目标。响应体最大值基本保持约 17KB，证明历史总量没有重新进入响应体；40 个请求对应 40 次分页查询，没有出现按总记录数逐条查询。

## 结果边界

这不是生产性能承诺，原因包括：

- 内存 SQLite 不包含生产磁盘同步和文件锁等待；
- `inject` 不包含 TLS、Nginx、网络延迟、压缩及浏览器解析；
- 单次运行不能替代长时间 P95/P99 监控；
- 测试数据结构稳定，不包含生产中最大长度备注、复杂审计正文和极端加密字段；
- 浏览器 DOM、切页焦点和移动端渲染由用户最终验收，本脚本不模拟这些行为。

最终发布前应复制脱敏生产快照到隔离目录，在相同服务器硬件上运行只读基准；随后通过反向代理测试并记录接口 P50/P95、SQLite busy/lock、CPU、RSS 和事件循环延迟。不得直接用生产账本运行写入型造数脚本。

## 仍需继续处理的全量扫描

代码复查发现的剩余全量读取分为三类：

1. `finance/costs` 已于后续阶段改成数据库筛选、搜索和分页，并将完整付款凭证延迟到订单详情读取，见《45-成本核算列表服务端分页》；不再属于页面全量扫描遗留项。
2. 支付、退款、发票及充值 Worker 的候选任务仍有部分全量扫描，应改为有界队列查询，避免订单增长后拖慢轮询。
3. 付款流水、退款流水和请求号的重复校验属于资金安全约束，不能简单截断；应逐步用数据库唯一约束或精确索引查询替代全量 `some/find`。

上述三类不得混为一谈。页面读取可以分页，后台任务必须有界，资金防重必须保持全局正确性。
